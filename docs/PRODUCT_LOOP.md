# 产品优化 Loop 机制（PRODUCT_LOOP.md）

> 目标：以**产品经理**为主导、多工程师协作，围绕 `docs/project_spec.md` §7 蓝图持续迭代；无人值守时也能自动推进，并在达到条件时**自行停止**，产出可追踪、可复用、可续跑的记录。

---

## 1. 角色与职责

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **产品经理**（主导） | 选题、排优先级、派工、验收、判停、写迭代报告 | 不写代码、不改 spec、不自判 UI |
| 技术负责人 | 接口契约 / 数据模型 / spec 权威 / 任务拆解；技术评审关卡 | 不大量写业务代码 |
| 后端开发工程师 | `server/` 实现 | 不改 spec、不碰 client/web |
| 小程序开发工程师 | `client/` 实现 | 不改 spec、不碰 server/web |
| Web管理后台开发工程师 | `web/` 实现 | 不改 spec、不碰 server/client |
| UI-UX 设计师 | 页面内信息布局与交互裁决（UI 缺陷最终裁定） | 不写业务代码 |
| 质量把控工程师 | 只读门禁检测，不合格回退 | 不改代码、不自判 UI |

**编排说明**：主 agent 在不单独 spawn 产品经理时代行其职责，决策规则以本文件与 `产品经理.md` 为准，保证机制可复用。

---

## 2. 单轮流程（六步，不可跳步）

1. **选题** —— 从 `docs/loop/STATUS.md` 候选池 + 上一轮遗留项选取，写明「本轮做完什么样算好」
2. **排优先级** —— P0 阻塞上线 / P1 正确性或体验受损 / P2 优化
3. **派工** —— 派给对应角色；指令必须含：背景、精确范围、验收标准、**结果写入哪个文件**
4. **验收** —— 逐条核；不合格即回退（附 `file:line` + 期望 + 现状）
5. **落盘** —— 写 `docs/loop/ITER-XXX.md`，更新 `docs/loop/STATUS.md`
6. **判停** —— 按 §4 判定；达标则停，遇阻塞则挂起

### 可靠性硬要求
子 agent 回报可能被截断，因此**所有交付物必须落盘**：派工时要求子 agent 把结果写入指定文件（如 `docs/loop/ITER-001-qa.md`），回报只写「完成 + 关键计数」。验收以**读文件**为准，不依赖回报文本。

---

## 3. 迭代目标（本机制下的价值排序）

1. **上线阻塞清零**（最高）：任何导致无法上线或上线即不可用的问题
2. **正确性与合规**：契约不一致、鉴权缺口、UGC 内容安全、金额/角色等一致性红线
3. **首版定位打磨**（§7.2「找吃的」）：搜索 / 筛选 / 推荐 / 导航
4. **运营效率**：管理员日常操作路径（如 §7.3 二期「一键转菜品」）
5. 打磨与重构（最低优先级，不得挤占前四项）

---

## 4. 停止条件（满足任一即停）

- **S1 目标达成**：本轮承诺的 P0/P1 全部闭环，且质量门禁无 🔴/🟠
- **S2 无米下锅**：候选池中已无 P0/P1，且剩余项均需用户决策或需线上环境
- **S3 阻塞挂起**：出现必须用户拍板的事项（产品取舍、密钥/部署、真实数据）→ 挂起并写明「等用户决策什么」
- **S4 收益递减**：连续两轮无实质产出（仅文档或格式调整）→ 停止并上报

停止不是失败：每轮停止都必须留下「下一轮候选」与「阻塞项」，保证可续跑。

---

## 5. 循环触发方式

- **手动续跑**（默认）：用户说「继续下一轮 / 继续迭代」→ 读 `docs/loop/STATUS.md` 接续
- **自动续跑**（可选）：用 automation 定时触发（如每天 `FREQ=DAILY;BYHOUR=2;BYMINUTE=0`），prompt 固定为「按 docs/PRODUCT_LOOP.md 执行一轮产品优化迭代，先读 docs/loop/STATUS.md」
- **事件续跑**：用户新拍板决议 → 技术负责人写入 spec §7 → 触发新一轮

## 7. 红线（任何一轮都不得违反）

- 不推翻 spec §7 已拍板决议；确需变更必须走「用户重新拍板 → 技术负责人写入 spec」
- 不引入新框架/新依赖
- 三端不越界改（server / client / web 各守各端）
- 数据库结构变更只改 `server/src/main/resources/db/` 脚本，禁直连 ALTER
- 涉密信息（密钥、口令）只落环境变量与 gitignore 文件，不入库

---

## 8. 问题流转机制（定型模糊问题的统一闭环）

工程师在实现中一旦遇到「业务定型模糊、规则冲突、契约缺口」，**不许自行拍板**，也不许各说各话；一律走唯一渠道登记并流转。

### 8.1 唯一渠道
`docs/loop/QUESTIONS.md`（问题登记表）是**唯一渠道**。所有问题必须登记在此，对话/口头结论一律不算（避免"聊过就忘、无人追踪"）。

### 8.2 触发条件（命中任一即须登记）
| 代号 | 触发条件 |
|---|---|
| T1 需求模糊 | 文档未覆盖或表述歧义，实现需要"猜"（凡出现"我觉得应该是…"即触发） |
| T2 规则冲突 | spec / tasks 两处口径不一致，或与 §7 蓝图定版决议冲突 |
| T3 契约缺口 | 前端需要的接口/字段/错误码/分页规范未被定义 |
| T4 实现约束冲突 | 技术要求与产品要求矛盾（例：产品要"实时可见"但机检必填 openid） |
| T5 环境/数据缺口 | 需真实密钥、线上环境或真实数据才能验证 |
| T6 边界未定 | 异常与极端场景未定义（重复提交、时效、上限等） |
| T7 决议疑似被推翻 | 实现中发现与历史拍板决议矛盾 |

### 8.3 记录方式（字段固定，缺字段视为无效登记）
`ID | 提出角色 | 时间 | 类型 | 一句话问题 | 证据(file:line / spec 条款) | 影响面 | 候选方案(≥2，含推荐) | 优先级 | 决策人 | 状态 | 决策结论 | 闭环证据`

- ID 形如 `Q-001`，只增不复用。
- **必须自带 ≥2 个候选方案与推荐**：只抛问题不给选项 = 把思考成本甩给产品经理，不允许。

### 8.4 优先级判定
| 级别 | 含义 | 时限 |
|---|---|---|
| **P0 阻塞** | 不决策就无法实现，或影响能否上线 | 当轮内 |
| **P1 重要** | 影响正确性 / 合规 / 核心体验 | 当轮或下轮 |
| **P2 一般** | 不影响主流程 | 两轮内 |
| **P3 观察** | 记录备查 | 无时限 |

客观升级规则：① 触及 §7 已拍板决议或合规 → 至少 P1；② 同一问题被重复提出 ≥2 次 → 自动 P0；③ 影响面 ≥2 端 → +1 级。

### 8.5 流转路径
```
工程师发现问题
  → 登记 QUESTIONS.md（带候选方案 + 推荐）
  → 产品经理：判优先级 + 定决策
      ├─ 涉及契约/数据模型 → 技术负责人更新 spec / tasks
      ├─ 涉及 UI 取舍      → UI-UX 设计师裁决
      └─ 涉及「产品定型」变更 → 必须由用户拍板（PM 只出推荐，不代替用户决定）
  → 派工实现 → 质量门禁验证 → 回填闭环（结论 + 证据 + 迭代号）
```

### 8.6 决策权归属（关键，防越权）
- **产品经理（agent）**：优先级判定、方案推荐、实现验收、loop 编排。
- **用户**：一切「产品定型」变更的最终拍板权（新功能、砍功能、改变已定蓝图）。
- **技术负责人**：契约、数据模型、spec 权威表述。
- **UI/UX 设计师**：页面内布局与交互取舍。

> **未决先行规则（保证无人值守不停摆）**：P0/P1 问题在用户不在场时，工程师可按**登记表里的推荐方案**先行实现，但必须在代码注释与 QUESTIONS.md 中标注「未决先行，待 PM/用户复核」；决策回来后若与实现不符，**必须按决策修正**，不得以"已实现"为由拒绝变更。P2/P3 不得先行。

### 8.7 反馈时限与超时处理
- P0 当轮内响应；无人值守时按 8.6 未决先行，并列入 `STATUS.md` 阻塞项（写明"等谁决策什么"）。
- 超时未决策的 P0 每轮在 ITER 报告中重复置顶，直到闭环。
- 工程师等待决策期间**不得停工**：转做不受该问题阻塞的其他任务。

### 8.8 闭环标准（5 条同时满足才算 closed）
1. 有明确决策：谁、何时、结论是什么
2. 决策已落到权威文档（spec §7 / tasks / 契约），**不是只存在于对话**
3. 代码/页面已按决策实现，且过质量门禁
4. QUESTIONS.md 该条状态置 `closed` 并附证据（`file:line` / commit / 迭代号）
5. 若决策推翻了旧决议，旧条款已同步修订，仓库内不留双重口径
