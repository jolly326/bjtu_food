## 产品定位

**校园菜品展示与轻量评分平台** —— 帮学生解决「今天吃什么」。菜品与档口信息由运营录入；学生只做三件事：**看海报、刷菜、点反馈**。

- **学生端三个 tab**（TabBar 显示名）：**风物**（看档口海报）｜ **美味**（卡片式一次一道，可点「去品尝」）｜ **记忆**（按月回看饮食记录、就地评分与纠错）
- **运营端**：食堂 / 档口 / 菜品 / 海报 录入 + 反馈数据查看
- **无搜索**；**无「我的」页面**
- **全匿名**：不做注册 / 登录 / 认证 / 注销；用户身份由微信 openid 静默识别，不在任何界面展示
- **无分享与文字 UGC**：学生侧仅「去品尝」「三态评分」「菜品纠错选项」三类动作

## 技术栈

- **后端**：**Python · FastAPI · SQLAlchemy · MySQL 5.7（TDSQL-C）**
- **学生端**：Vue 3 + TypeScript · uni-app（微信小程序）
- **运营端**：Vue 3 + TypeScript + Vite
- **质量门禁**：后端 **pytest** + **分层护栏**（`import-linter` 等静态依赖检查）；前端 `vue-tsc` / `check:contract` / `vitest`

## 变更流程

1. 改**代码**时同步更新对应层文档（先按上表定位归属）。
2. 改**契约**（后端模型 / 端点）后需刷新端上类型：由 agent 本地启动后端（**仅限**抓取契约快照 `GET /openapi.json`）并执行 `client/` 下 `npm run gen:api:fresh`，随后跑 `npm run verify`。
3. 改**库表**：先改 [`schema/`](./schema/README.md) 对应表文档（唯一真源），再直连远程库执行 `ALTER` / `CREATE`；**禁只 ALTER 不同步文档**。
4. 提交前跑质量门禁：
   - 后端：`pytest`
   - 前端：`cd client && npm run verify`

## 约定

- 文档只写**当前口径**：变更过程与修订轮次不维护（需回溯从 git 历史查）。

## 已知取舍

| 项 | 取舍 | 理由 |
|---|---|---|
| 好评度分数 / 评价明细 | **学生端不展示**（无详情页）；运营端保留 `avgReaction`、投票人数与记录明细 | 守住「无二级页面」红线 |
| `avgReaction` | 学生端出参**不下发**（端上零消费）；运营端 `DishVO` 仍下发 | 学生端展示一律用 `flavorLevel`；服务端推荐权重与评级判定仍需均值 |
| 记忆卡字段 | **有位置 · 价格**（`食堂 · 档口 · N元`），**无风味评级**（评级只在菜品卡） | 记录出参不带 `flavorLevel`：卡面已有更强的「题目 + 图 + 位置价格」，再叠评级会抢主体 |
| 运营「菜品管理」风味评级列 | 运营端仅展示 `avgReaction` 与投票人数（无评级列） | 评级是学生端展示口径，由同一缓存列实时判定、不落库 |
| 风物页卡片内文案 / 主按钮 | **不做** —— 海报卡只承载海报图（无叠字、无 CTA） | 档口信息已画入海报；避免与图上文案重复，且无目标动作 |
| 图标资源库 | 两端**同源预置**（`client/src/assets/icons` 与 `web/src/assets/icons`），未消费的图标键**保留不删**；门禁只提示、不阻断 | 复用同一套 Lucide 资源，避免两端图标集漂移 |
| 深色模式原生窗口底 | `pages.json` 窗口 / TabBar 底必须字面 hex，**不随主题切换** —— 冷启动与切换瞬间有短暂暖白底 | 平台限制（微信校验要求 hexColor）；暗色界面经 CSS 变量全站切换，首屏瞬时浅底可接受 |
| 深色模式不跟随系统 | 仅手动切换 + storage 持久化，默认浅色；入口暂仅风物页 Header | 跟随系统会使首屏底色不可控，与「安静、确定性」的品牌调性不符 |
