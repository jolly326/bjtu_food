# correction — 菜品问题反馈

**用途**：用户对菜品提出的**问题反馈**，由管理员核实后处置。**只存提交事实**（append-only）。**两类**：

| `type` | 语义 | 表单 |
|---|---|---|
| **`field`**（默认） | **信息有误** | 有表单：仅提交**改动项**快照 |
| **`gone`** | **已经下架** | **一键提交即可成立**；说明与图片为**可选补充** |

**对应实体**：`com.bjtufood.correction.entity.Correction`

> 本表**无状态列** —— 「是否已处置 + 结论 + 处置文案 + 处置人」外置在 [moderation_task](./moderation_task.md)（多态键 `('correction', type_id)`）。

---

## 列定义

| 列 | 类型 | 可空 | 默认 | 键 | 说明 |
|---|---|---|---|---|---|
| `id` | BIGINT | NO | AUTO_INCREMENT | PK | 反馈 ID |
| `type` | VARCHAR(16) | NO | `'field'` | KEY | **`field`=信息有误 / `gone`=已经下架** |
| `dish_id` | BIGINT | NO | — | KEY | 被反馈的菜品；**不设外键**（见下） |
| `user_id` | BIGINT | NO | — | **FK** | 提交人；**外键 `fk_correction_user` → `user(id)`**（无级联）。提交入口一律需登录态 ⇒ **恒为真实用户 ID** |
| `name` | VARCHAR(64) | YES | NULL | | 改动后的菜名；**未改动则 NULL**。`gone` 型恒 NULL |
| `price` | INT | YES | NULL | | 改动后的现价（**单位分**）；未改动为 NULL。`gone` 型恒 NULL |
| `canteen_name` | VARCHAR(64) | YES | NULL | | 改动后的食堂名；未改动为 NULL。`gone` 型恒 NULL |
| `stall_name` | VARCHAR(64) | YES | NULL | | 改动后的档口名；未改动为 NULL。`gone` 型恒 NULL |
| `images` | JSON | YES | NULL | | 图片数组。**`field` 型**：改动后的图片；**`gone` 型**：**可选补充**。**两类上限同为 3 张**（全站 UGC 配图同档） |
| `note` | VARCHAR(200) | YES | NULL | | **补充说明**（≤200 字）。**仅 `gone` 型的选填补充**，其余 NULL |
| `created_at` | DATETIME | NO | `CURRENT_TIMESTAMP` | | 提交时间 |
| `attributes` | JSON | YES | NULL | | 改动的描述属性（**仅改动的维度**）；未改动为 NULL。`gone` 型恒 NULL |
| `floor` | VARCHAR(16) | YES | NULL | | 用户提交的楼层；未提交为 NULL。**归属档口**（管理员在 A2 档口管理手动修改 `stall.floor`）。`gone` 型恒 NULL |

## 索引

| 索引名 | 列 | 类型 | 用途 |
|---|---|---|---|
| `PRIMARY` | `id` | 主键 | |
| `idx_correction_dish` | `dish_id` | 普通 | 按菜品查反馈 |
| `idx_correction_type_dish` | `type`, `dish_id` | 复合 | **详情「N 人反馈已下架」（`goneUserCount`）**：`WHERE type='gone' AND dish_id=?`，再按处置任务行 `pending` 过滤 |
| `fk_correction_user` | `user_id` | **外键** | `REFERENCES user(id)`（**无级联** —— `user` 行永不物理删除，外键是纯引用完整性兜底） |

> 处置状态不在本表 ⇒ 复合索引只覆盖 `type` + 目标维度；「待处置」筛选由 `EXISTS (… moderation_task …)` 承担（见 [api/web/corrections.md](../api/web/corrections.md)）。

## 关键设计

### 两类反馈的语义差别（`type` 存在的理由）

| | `field`（信息有误） | `gone`（已经下架） |
|---|---|---|
| 前提假设 | **这道菜存在，只是信息写错了** | **这道菜消失了** |
| 差异项列（name/price/…） | 存改动项，未改动为 NULL | **恒全 NULL**（无可对照的原值） |
| 承载信息 | `images`（≤3）+ `attributes` | **`note`（≤200 字，选填）+ `images`（≤3，选填）** |
| 处置动作 | **管理员阅读后在 A3 菜品管理手动修改**（不自动写回） | **管理员阅读后在 A3 菜品管理手动下架**（可逆），见下方红线 |
| 处置可逆性 | 手动修改本身可再修正 | **下架可重新上架**（评价完整保留） |

> ⚠️ **`gone` 型必须承载「选填补充」**（`note` / `images`）：单靠「一键提交」会抹平两类**对管理员完全不同**的判断：
> - 「**变成了别的菜**」⇒ 信息可补录，无需下架
> - 「**换窗口了**」（菜还在，只是位置变了）⇒ 属 `field` 型，改档口即可
> - 「**今天临时没供**」⇒ 也许明天就恢复，**是否该下架**需要判断
>
> ⇒ 口径为「**一键提交 + 选填补充**」：**提交成本仍为 0**（不填也能提交），同时让上述场景在处置时可见。

### 🔴 红线：`gone` 反馈的处置只能是「下架」，绝不能是「删除」

| 操作 | 语义 | 数据层 | 评价 | 可逆 |
|---|---|---|---|---|
| **下架** | 暂时不在售 | `status='off'` | **保留** | ✅ **可重新上架** |
| **删除** | 彻底移除 | **物理删除** | 🔴 **级联删除**（`ON DELETE CASCADE`） | ❌ **不可逆** |

> **为何写死**：`gone` 反馈**天然含误报**（用户可能看错窗口、菜品只是临时售罄）。若允许在该流程中删除，则「**一次误报 + 一次点错 = 该菜全部历史评价永久消失**」，而评价是**不可再生资产**。
>
> ⇒ **删除只允许在 [A3 菜品管理](../func/web/A-主数据维护/A3-菜品管理.md) 由管理员主动执行**（带二次确认，明示「将一并删除 N 条评价」）；**处置 `gone` 反馈的界面不得出现「删除」按钮**。

### ⚠️ 无「下架阈值」：≥1 条即进待办，是否下架由人工决定

| 环节 | 规则 |
|---|---|
| **进入待办队列** | **≥1 条即进**（按 `user_id + dish_id` 去重后）—— 去重是**防单人刷队列**，**不是决策门槛** |
| **是否下架** | **管理员人工决定**；系统**不自动下架** |
| **驳回** | 必填处置文案（不采纳原因，落 `moderation_task.reply_content`），回执告知用户「经核实仍在售」 |

> **本表不设任何「阈值」列** —— 「≥N 独立用户」属**活跃度阈值**（判断信息新鲜度，与是否下架无关），与本表的处置流程**无关**。
> **依据**：进队列 ≠ 自动下架；管理员看到的是「有人反馈 + 可选说明/图片」，判断成本本就很低。设门槛只会让**用户的反馈石沉大海**。

### 局部提交 = 只存改动项
请求体**只传用户改过的字段**，未改动列在库中**留 NULL**。

因此本表**不是菜品副本**，而是**「改动项快照」**—— 管理端详情把它与菜品现状**并排对照**（当前值 / 提交值 + 是否一致），供管理员阅读后**在 [A3 菜品管理](../func/web/A-主数据维护/A3-菜品管理.md) 手动修改**作参照（**不自动写回**）。

⚠️ 代价：**无法区分「用户把某字段清空」与「用户没改该字段」**。当前所有字段均不接受空值提交，故不构成问题；若将来允许清空某字段，需引入显式的变更标记。

### `dish_id` 不设外键 —— 菜品删除后反馈记录有意保留

| 若设 | 后果 |
|---|---|
| `ON DELETE CASCADE` | 删除菜品会**连带删掉反馈记录** —— 丢失「用户反馈过什么」的历史痕迹 |
| `ON DELETE RESTRICT` | **菜品永远删不掉** —— 只要有过反馈记录就被卡住 |

反馈记录是**独立的历史数据**（用户诉求的留痕），不是菜品的附属数据，因此两个选项都不可接受。

### 楼层归属档口，不归属菜品
`floor` 提交值仅作记录，实际楼层由管理员在 [A2 档口管理](../func/web/A-主数据维护/A2-档口管理.md) 手动修改**目标档口**的 `stall.floor`，因此：

> ⚠️ **改动楼层会同时影响该档口下的所有菜品。**

这是刻意设计（楼层是场所属性），管理员在 A2 修改时须知晓连带影响。

### 不纠正原价
**无 `original_price` 快照列** —— 原价随促销波动、属运营口径，短期打折不构成稳定事实，因此不纳入菜品问题反馈范围。`price` 是唯一可反馈的价格字段。

## 关联

| 方向 | 目标表 | 关系 |
|---|---|---|
| N→1 | `dish.id` | 被反馈菜品（**无外键**，见上） |
| N→1 | `user.id` | 提交人 —— **外键 `fk_correction_user`（无级联）**：提交入口一律需登录 ⇒ `user_id` 恒为真实用户；账号注销为匿名化（行保留），无级联需求，外键只保证不悬空 |
| 1—1 | `moderation_task`（`type='correction'`） | 处置状态机 —— **多态键 `(type, type_id)`，无外键**，唯一索引保证 1:1 |

`field` / `gone` 均由管理员**阅读后**在 [A3 菜品管理](../func/web/A-主数据维护/A3-菜品管理.md) **手动**修改或下架（**系统不自动写回、不自动下架**）；`gone` 的下架为可逆动作，**绝不物理删除**（红线见上）。

## 注意事项

- **`attributes` 快照列定位**：作为「用户提交记录（中文原文留痕）」存在，**不是菜品属性的副本**，也不参与任何写回菜品链路；`images` / `note` 同理，均为提交事实。
- `attributes` 快照**仅含改动的维度**，不是菜品属性的完整副本。
- ⚠️ **`attributes` 快照键 = 维度 ID**（JSON 内为字符串形态的 `dish_attribute_dimension.id`，与 `dish.attributes` 键形态一致），**值是用户提交的「中文」，不是取值 ID**：用户可自由输入字典之外的新值，而**提交反馈不写库**。本列**仅是用户提交记录（中文原文留痕）**，供管理员阅读后在 A3 手动修改菜品时参照；取值 ID 的解析与字典登记（命中即用、**未命中新建**）发生在 A3 菜品编辑链路，不在本反馈流程内。登记入口见 [dish_attribute_value](./dish_attribute_value.md)。
- ⚠️ **`note` / `images` 对 `type=gone` 均为「可选补充」** ⇒ 库层**不设 NOT NULL**；`gone` 行的各差异项快照列**恒 NULL**（语义是「无可对照的原值」，**不是**「未改动」）。
- 库内当前 **1 行**（直连生产库核对），其处置任务行为 `pending`。
