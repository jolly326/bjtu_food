## 1. 后端是否迁移 Python（为后期接入模型）

- **背景**：「接入模型」的真实场景未定 —— 调 API 生成文案 / 语义搜索 / 内容审核 / 本地推理，四者对语言的要求完全不同。
- **现状**：后端 Java 21 · Spring Boot 3.2（**298 个主代码 + 56 个测试**）。
- **选项**：**A** 维持 Java（调模型 API 用 Spring AI / `WebClient` 即可）｜ **B** 并列一个 Python 推理服务（Java 后端经 HTTP 调用，零返工）｜ **C** 全量重写为 Python。
- **我的建议**：**A 或 B**。接入大模型本质是 HTTP 调用，语言不构成门槛；Python 的独占优势只在本机推理与训练。若选 **C**，需同时满足：极简改造后剩余量级很小 **且** Python 为团队长期主力。

## 2. 评分形态：三态（好吃 / 一般 / 踩）还是两态（赞 / 踩）

- **背景**：先前提法为三态，后表述为「点赞点踩等基础评分」。
- **选项**：**A** 三态 ｜ **B** 两态。
- **我的建议**：待定 —— 直接决定「好评率 / 推荐度」的公式与卡片展示口径。

## 3. `docs/old/` 归档区的处置

- **现状**：旧体系 126 份文档已归档至 `docs/old/`（`git mv` 保留历史，已 stage 为 rename，**未 commit**）。
- **选项**：**A** 入库 git，立规「`old/` 非真源、不参与文档一致性与命名约束」｜ **B** 改名为 `docs/.archive/`（点开头天然被多数工具忽略）｜ **C** 不入库（从 git 移除）。
- **我的建议**：**A**。理由：真源须可 diff / 可回滚，归档同理。**连带项**：`check:doc` / `check:ui` 等门禁脚本的扫描范围需排除归档区（属代码改动，需明示后执行）。

## 4. 学生端身份凭证与防刷

- **背景**：「全匿名 + openid 分辨用户」在实现上有两种形态，安全强度差别很大。
- **选项**：**A** 服务端签发凭证 —— 冷启动静默 `POST /auth/wechat-login`（`wx.login` code 换 openid）→ 服务端建 / 取 `user` 行 → 下发 token；端上**不传 openid** ｜ **B** 端上直传 openid（无凭证）。
- **我的建议**：**A**。`B` 意味着任何人可伪造他人 openid 刷票 —— 而评分**影响排序**，被刷即刻成为用户可见危害；且 openid 属敏感个人信息，散落在业务表不利于清理。
