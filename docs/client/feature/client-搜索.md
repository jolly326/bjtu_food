# 搜索（A-03）

> 所属端：**学生端（微信小程序）** ｜ 鉴权：**🔓 公开**（免登录）
> 返回：[功能总览](./README.md)

## 介绍

按关键词找菜。页面**只有三件事**：**搜索**（关键词检索菜品）、**搜索记录**（**纯本地**，不上服务端）、**猜你喜欢**（**后端随机推送菜品**——无推荐算法、无热度排序、无个性化；随机性按**会话**收敛：端上传会话级 `seed`，同一次会话内多次进入拿到**同一批**词条，**重进小程序**才整体重洗）。输入关键词即调 `GET /dishes?keyword=…` 展示结果，该词**写入本地搜索记录**（去重、最新在前、上限 4 条；支持清空，无记录时整块不渲染）。

> **搜索记录写入口径**：**用户主动发起的搜索都写入**——① 显式提交（回车 / 点「搜索」按钮）、② **点「猜你喜欢」词条**；**仅点「搜索记录」自身词条重搜不写入**（已在记录内）。上限 4 条，去重、最新在前。
> **状态口径**：清空搜索框 = 清词 **并** 退回发现态（不残留旧结果）；左上角返回 = **恒退出本页**（详见 [`docs/client/ui/`](../ui/) §4.1）。

## 接口

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/dishes?keyword=…` | 🔓 公开 | 关键词搜索：**同一端点**复用于首页网格与搜索；对菜名 / 档口名 / 食堂名**三处**模糊匹配（`DishMapper.xml`） |
| GET | `/dishes/for-you` | 🔓 公开 | **猜你喜欢**：**随机抽取在售菜品名**下发（`[{ name }]`）——不看热度、不排序、**不做推荐算法**。随机性按**会话**收敛：端上传会话级 `seed` ⇒ 同一次会话内多次进入拿到**同一批**词条，**重进小程序**才整体重洗；不传 `seed` ⇒ 服务端退回 `ORDER BY RAND()` 真随机（参数**可选**）。**契约留扩展位**——将来升级为个性化 / 推荐算法时**端上契约不变**（仍 `name` 列表），只换服务端取数逻辑 |

## 字段

### 请求 · `GET /dishes`

| 字段名 | 类型 | 必填 | 中文解释 |
|---|---|---|---|
| `keyword` | string | 否 | 关键词，**同时匹配菜名 `dish.name` / 档口名 / 食堂名**（`DishMapper.xml` 三处模糊匹配；空则不筛选） |
| `page` | number | 否 | 页码，默认 1 |
| `pageSize` | number | 否 | 每页条数（**搜索页固定传 20**，`RESULT_PAGE_SIZE`）；服务端归一化上限 **100**（`PageUtil.MAX_PAGE_SIZE`，超限截断） |

> **`GET /dishes` 完整参数集 = `page` / `pageSize` / `keyword` / `view` / `seed`**（`view` 为筛选视图键，搜索页不传；`seed` 为会话随机种子，**搜索页不传**——且仅对推荐类视图生效，搜索流恒为服务端热度口径）；搜索结果排序不传参、无排序入口。

### 响应 · `GET /dishes`（`data` = `PageResult<DishListItemVO>`）

**分页外壳字段**：

| 字段名 | 类型 | 中文解释 |
|---|---|---|
| `records` | DishListItemVO[] | 当前页命中菜品行数组（端上以它为准） |

> 分页壳恒为 `records` 一项；结束判据 = 本次返回条数 < 请求的 `pageSize`。

**行字段 `DishListItemVO`（列表专用 8 字段）**：

> **字段集与逐字段中文口径以 [client-首页菜品浏览](./client-首页菜品浏览.md) 的 `DishListItemVO` 表为唯一真源**（本文档不重复维护，避免同一契约出现两份措辞并漂移）。

> **8 字段均全量消费**：结果卡**渲染位置行**；**不为搜索另拆 VO**（多一个 VO 即多一份契约维护成本）。
> **详情专属字段不在列表出参中**：`description` / `images[]` / `floor` / `attributes`（`DishDetailVO` **共 11 字段**）。
> 搜索结果卡片与详情页均**不显示距离**（无定位、无 Haversine）。

### 请求 · `GET /dishes/for-you`

| 字段名 | 类型 | 必填 | 中文解释 |
|---|---|---|---|
| `seed` | string | 否 | **会话随机种子（会话级）**：端上**冷启动生成一次、会话内恒定**（重进小程序才重掷）。传 ⇒ 服务端按 `CRC32(CONCAT(seed,'-',d.id)), d.id` 做**稳定伪随机序**，同一次会话内多次进入拿到**同一批**词条；**不传** ⇒ 服务端退回 `ORDER BY RAND()` 真随机（参数**可选**，旧端 / 第三方 / Swagger 直连不受影响） |

### 响应 · `GET /dishes/for-you`（`List<GuessLikeVO>`）

| 字段名 | 类型 | 中文解释 |
|---|---|---|
| `name` | string | **菜品名**（随机抽取的在售菜品）；**端上唯一消费字段**（chip 文案 + 点击起搜） |

> **语义**：服务端**随机抽取**在售菜品（`status='on'`）的 `name` 下发——**不按热度排序、不做个性化、不与用户历史相关**（「随机」即需求本身）；条数由**服务端固定为 6 条**，端上**不写死条数与文案**、按返回渲染、空数组则整块不渲染。
> **刷新边界 = 重进小程序**：端上**没有任何「主动换一批」入口**（全仓无 `onPullDownRefresh`）——用户无法解释内容为何变化，只能读成「界面不稳定」。故随机性归于**会话**：端上传会话级 `seed`，服务端按 `CRC32(seed:ID)` 稳定伪随机序取数（与推荐流 `selectDishPage` 的 `SEED_RANDOM` 分支**同一套算法**，`d.id` 作决胜键消除 CRC32 并列乱序）⇒ 同一次会话内多次进入拿到同一批词条，**重进小程序**才整体重洗。
> **`seed` 与推荐流同源不同值**：端上用同一会话基准（`stores/dish.ts` 的 `sessionSeedBase`）派生两个种子（`-home` / `-guess`）——若共用同一 `seed`，两处取的是同一全序的前 N 个 ⇒ 首屏与发现态出现**同一批菜**（观感像 bug）。
> **取数演进预留**：当前 `CRC32(seed:ID)` 全序排序在数据量级增长后应改为「随机主键区间取数」，**端上契约不变**（仍为 `name` 列表）。
> **不缓存响应**：本端点仍不加进程内读缓存——「会话内稳定」已由 `seed` 表达在数据层；若再加 TTL 型缓存，**缓存键必须含 `seed` 才有意义**（否则不同会话互相串味），收益与复杂度不成正比；真随机分支（未传 `seed`）更与缓存语义直接冲突。
> **出参只有 `name`**：随机语义下无其他消费点——小程序（`types/dish.ts` 为 `{ name }`）对其他字段**零消费**，属「零消费即删」。
> **零消费即删**：若将来 chip 要展示图片 / 价格，再按端上真实消费扩字段（不为「以后可能用到」预埋）。
