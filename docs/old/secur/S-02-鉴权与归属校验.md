# S-02 · 鉴权与归属校验

> **等级 S（核心防线）** —— 缺失即失守：攻击者**不需要任何漏洞**，注册个账号改 URL 里的 `{id}` 就能删/改他人数据。这是校园场景最先被尝试的路径。
> **范围**：对象级授权（IDOR）逐端点矩阵、角色与权限边界、端点与错误码。
> **真源**：本文档。身份与凭证见 [S-01](./S-01-身份与凭证.md)；参数与字段校验见 [A-01](./A-01-参数与字段校验.md)。

---

## 1 · 对象级授权（IDOR 防护）—— 主要威胁面

**攻击形态**：攻击者用**自己的合法 token**，篡改路径 / 请求体里的 `{id}` / `{reviewId}` / `userId`，去读或改**别人的资源**。

### 1.1 · 判定口径（硬约束）

| # | 约束 |
|---|---|
| 1 | 资源归属判据 = **查询资源的 `user_id` 与 `SecurityUtil.getCurrentUserId()` 相等**，不得依赖请求体传入的 userId |
| 2 | 归属不符 ⇒ **`403`**，回统一文案（**不区分**「不存在」与「无权限」的措辞差异，避免探测） |
| 3 | 写操作以 **JWT 内 userId** 建立归属（如「我的评价」按 `userId + dishId` 锁定行），**从设计上无法写到他人行** |
| 4 | **不提供批量写端点**；若将来出现，须**逐项**校验归属 |

### 1.2 · 归属校验矩阵（逐个写端点核对）

| 端点 | 归属判定 | 位置 |
|---|---|---|
| `DELETE /reviews/{id}` | ✅ `review.user_id == 当前 userId` | `ReviewServiceImpl` |
| `POST /dishes/{id}/reviews` | ✅ 按 `userId + dishId` 锁定/覆盖，写不到他人行 | `ReviewServiceImpl` |
| `PUT /my/notifications/{id}/read` | ✅ `notification.user_id == 当前 userId` | `NotificationServiceImpl` |
| `PUT /auth/profile` | ✅ 只操作自身（userId 仅来自登录态） | `AuthController` → `AuthServiceImpl` |
| `DELETE /auth/account` | ✅ 只操作自身 | `AuthController` |
| `POST /feedback` · `POST /dishes/{id}/correction` · `POST /reviews/{id}/report` | 仅建单、无「他人资源」语义；`userId` 一律取当前登录态（**写入口恒需登录**） | 各 Controller |

> **核对结论**：学生端全部按 `{id}` 操作的写端点**均已具备归属校验**，无缺口。防回退约束：**新增任何带 `{id}` 的写端点，必须同步补归属校验并登记进本表**。

## 2 · 角色与权限边界（管理端 Zone A）

**三档角色**（`admin.role`），由 `AdminAuthFilter` 按「**HTTP 方法 + 角色**」在**服务端强制**判定：

| 角色 | 可做什么 | 典型用途 |
|---|---|---|
| `super` | 全部（含**删除**类不可逆操作） | 博主 / 负责人 |
| `operator` | 读 + **业务写**（新增 / 修改 / 处置 / 启停），**不含删除** | 日常运营 |
| `viewer` | **仅读**（`GET` / `HEAD` / `OPTIONS`） | 只读查看 / 观摩 |

| 约束 | 口径 |
|---|---|
| 门控位置 | **服务端强制**（过滤器按方法 + 角色判定）；前端按角色隐显入口只是**体验**，绕过前端直接调接口同样被拦 |
| 拒绝方式 | **`403`**（**非 `401`**）—— 身份有效、仅权限不足；用 `401` 会把用户无谓地踢出登录 |
| 未知角色 | **一律按 `viewer`（只读）处理**（fail-closed：数据异常时宁可少给权限） |
| 越权记录 | 每次越权尝试记 WARN（含路径与来源 IP），越权本身即安全信号 |
| 授权标记 | 认证上下文同时授予 `ROLE_ADMIN` 与 `ROLE_ADMIN_<角色>`，供后续接口级门控使用 |
| **自助端点例外** | `/admin/auth/password` 作用于「本人账号」，**不受角色门控**：只读角色同样需要能改自己的口令。仍要求有效 token |

**前端隐显口径**（判据收敛在 `web/src/utils/permissions.ts`，与服务端同源）：`viewer` 不显示写入口（新增 / 编辑 / 处置 / 启停），`operator` / `viewer` 均不显示**删除**入口 —— **仅 `super` 可见删除**。角色缺失 / 未知一律按 `viewer` 处理（fail-closed，与服务端 `normalizeRole` 同口径）。

## 3 · 端点与错误码

| 端点 | 鉴权 | 作用 |
|---|---|---|
| `POST /admin/auth/login` | 🔓 **必须在白名单内** | 账号密码换 token |
| `GET /admin/auth/me` | ✅ 需 token | 回当前管理员账号信息（前端确认登录态 + 回填角色与安全提示） |
| `POST /admin/auth/password` | ✅ 需 token（**自助，不受角色门控**） | 改密（并吊销既有 token，回新 token） |

| code | 条件 | 端上行为 |
|---|---|---|
| `401` | 未带 token / token 失效 / 账号已停用 / **凭证版本已失效（改密）** / 登录失败 | **清 token → 跳登录页** |
| `403` | 已认证但角色不足（只读角色写操作 / 非 `super` 删除） | 提示无权限（**不触发重新登录**） |
| `4001` | 资源不存在 | 与 `403` 的措辞不区分（避免探测） |

> 🔴 **`POST /admin/auth/login` 若漏加白名单 ⇒ 必 401，功能完全不可用**（登录请求自身被拦截）。这是本条设计最易踩的坑。

## 4 · fail-closed

| 场景 | 行为 |
|---|---|
| 未配置 secret | 启动失败 |
| 缺 token / URI 解析异常 | 一律拒绝（按 `401` 处理），不放行 |
| 未知角色 | 按 `viewer`（只读） |

## 5 · 危险访问路径：识别 / 拦截 / 响应

| 路径 | 识别 | 拦截 | 响应 |
|---|---|---|---|
| **IDOR**（篡改 id 操作他人资源） | 归属校验不通过 | `403` | — |
| **越权读**（读他人资料 / 通知） | 归属校验 / VO 白名单 | `403` / `4001`（不区分不存在与无权限） | 告警（高频时） |
| **越权写**（`viewer` 直调写 / 非 `super` 直调删除） | 方法 + 角色门控 | `403` | 越权 WARN（含路径与来源 IP） |
| **参数篡改 / 字段注入** | DTO 约束 + 拒绝未声明字段 | `400` | 高频异常 ⇒ 告警 |
| **身份自述**（请求体传 `userId` / openid） | 服务端只认 JWT 与 `code2Session` 结果 | 忽略 / `400` | — |
