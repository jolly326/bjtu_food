# B2 · 意见反馈管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**B UGC 治理**
> **口径要点**：处置状态**以处置任务表为判据**（`pending` / `handled`）；`outcome` 显式落列（`handled` 通过 / `rejected` 不采纳）；**文案只有一列**——`rejected` 的不采纳原因并入 `replyContent`（必填）；**不做批量处理**。

## 介绍

处理学生提交的**意见反馈**（独立资源 `feedback`，**只存提交事实**；类型由 `feedback_option` 字典表达，列表类型筛选即字典项筛选）。

**动作恰好两个**：**通过（`handled`）** 或 **不采纳（`rejected`）**；处理结果向提交人投递**站内回执**（对齐 [web/README](../README.md) 的「处置回执」口径）。

**职责边界**：

- **举报是独立资源，不在本页** —— 走 [B3 举报管理](./B3-举报管理.md)（独立列表、独立处理端点）；本页**无板块分流参数**，列表只有反馈一种资源；
- 本页**不碰**评价（B1）、菜品（A3）、菜品问题反馈（B4）等被处置对象。

**处置状态口径**：反馈表自身**无状态列**——`status` 以处置任务表为判据（`moderation_task` 的 `type='feedback'` 行）；「未处置」是**显式 `pending` 行**（提交时同事务预建），不是某列的空值。

## 接口

端点 / 入参 / 出参 / 错误码见 [**api/web/feedback.md**](../../../api/web/feedback.md)（意见反馈契约唯一真源）。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `feedback` | 读（正文 / 配图 / 类型 / 提交人） | 反馈提交事实本体，**处置不改写** |
| `moderation_task` | 读写（`status` / `outcome` / `reply_title` / `reply_content` / `handled_by` / `handled_at`） | 处置状态机与处置文案真源（多态键 `type='feedback'`，1:1） |
| `notification` | **写**（处置回执快照） | 站内回执，与处置**同一事务**写入 |

> 列口径见 [schema/feedback.md](../../../schema/feedback.md) 与 [schema/moderation_task.md](../../../schema/moderation_task.md)。处理动作**不改**反馈提交事实（正文 / 配图 / 类型 / 提交时间），历史不可被处置污染。

## 回执文案

| 结论 | 标题 | 正文 |
|---|---|---|
| `handled`（通过） | 反馈已处理 | 管理员填写的处置文案；留空用缺省文案 |
| `rejected`（不采纳） | 反馈未采纳 | **不采纳原因**（即 `replyContent`，必填，纯空白 → `400`） |

- **投递口径** —— 提交入口**恒需登录**（`user_id` 恒为真实用户）⇒ **一律投递**（含静默登录的游客）；投递与处置**同一事务**；
- **处置不可重复** —— `status != 'pending'` 再处理 → `400`「该记录已处理」（防结论被静默改写 + 回执重复投递）；
- **回执标题可选** —— `replyTitle`（≤40 字）留空按（类型 + 结论）用缺省文案。

## 备注（架构取舍）

- **`outcome` 是任务表的物理列**：「通过 / 不采纳」可从行本身判定，不靠文案推断；`status='handled'` 时必填。
- **文案只有一列（`replyContent`）**：不采纳原因并入其中，无独立「拒绝理由」字段；`rejected` 必填原因保证回执可读，`handled` 允许缺省文案保证「不逼人说废话」。
- **`handled_by` 记录处置人**：列表以 `handledByName` 呈现「处理人」。
- **不做批量处理**（单条处理已覆盖当前量级，留作演进）。
