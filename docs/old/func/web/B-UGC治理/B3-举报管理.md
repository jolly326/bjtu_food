# B3 · 举报管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**B UGC 治理**
> **口径要点**：举报是**独立资源**（独立列表、独立处理端点）；列表/详情**内嵌被举报评价**；**受理可联动隐藏**被举报评价（一次调用）；**被举报评价已删除**时举报行保留、列表以「评价已删除」表达；回执**按结论分流文案**并在受理时说明「对评价做了什么」。

## 介绍

处理学生提交的**评价举报**（独立资源 `report`，**只存提交事实**）—— **受理（可联动隐藏被举报评价）** 或 **不予处理**，并向举报人投递站内回执。

**职责边界**：只管**举报这条记录 + 对评价的处置联动**。

- **与 [B2 意见反馈管理](./B2-意见反馈管理.md) 是两个独立资源**（各自成表、各自成端点），菜单独立、列表字段与处置动作不同；
- **评价本身的治理**（隐藏 / 恢复 / 删除）在 [B1 评价管理](./B1-评价管理.md) —— 本页只在**受理**时**联动隐藏**一次，不提供「恢复显示」（恢复走 B1）。

**举报数据形状**（写入侧见 [api/client/reviews.md](../../../api/client/reviews.md)）：

举报**无正文**——结论以**结构化原因单选**为准（`option_id` 锚在 [A7 举报原因管理](../A-主数据维护/A7-举报原因管理.md) 的字典，仅启用项可提交）；被举报目标固定为**评价**（`review_id`）。

**前置规则（写入侧，供对照）**：目标必须公开可见（已隐藏 / 已删除不可被举报）；同一登录用户对同一评价不重复举报。

**被举报评价已删除**：举报行**保留**、`review_id` 置空（无清扫逻辑），举报人 / 原因 / 处置状态 / 处置文案**全部完整**——列表以「被举报评价已删除」呈现，评价摘要与可见性一并置空。

**处置状态口径**：举报表自身**无状态列**——`status` 以处置任务表为判据（`moderation_task` 的 `type='report'` 行）；「未处置」是**显式 `pending` 行**（提交时同事务预建）。

## 接口

端点 / 入参 / 出参 / 错误码见 [**api/web/reports.md**](../../../api/web/reports.md)（举报契约唯一真源）。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `report` | 读（举报人 / 原因 / 被举报评价 ID） | 举报提交事实本体，**处置不改写** |
| `moderation_task` | 读写（`status` / `outcome` / `reply_title` / `reply_content` / `handled_by` / `handled_at`） | 处置状态机与处置文案真源（多态键 `type='report'`，1:1） |
| `review` | **写**（受理并联动隐藏时置为隐藏，幂等） | 联动隐藏被举报评价 |
| `dish` | 评分聚合经事件**重算** | 隐藏评价会影响菜品均分 |
| `notification` | **写**（处置回执快照） | 站内回执，与处置**同一事务**写入 |
| `user` | **只读**（举报人昵称 + 被举报评价作者昵称） | 双方展示 |

> 列口径见 [schema/report.md](../../../schema/report.md) 与 [schema/moderation_task.md](../../../schema/moderation_task.md)。
> 隐藏评价**复用 B1 的同一套语义**（`is_hidden` 是唯一可见性判据、评分同步重算），不另立「举报隐藏」状态。

## 回执文案（**按结论分流**）

| 结论 | 标题 | 正文 |
|---|---|---|
| `handled`（受理）+ 本次隐藏了评价 | **举报已受理** | 说明「已隐藏该评价」+（有填写文案时）附处置文案 |
| `handled`（受理）+ 未动评价 | **举报已受理** | 管理员填写的处置文案；留空用缺省文案 |
| `rejected`（不予处理） | **举报未采纳** | **不采纳原因**（即 `replyContent`，必填，纯空白 → `400`） |

- **投递口径**：提交入口**恒需登录**（`user_id` 恒为真实用户）⇒ **一律投递**（含静默登录的游客）；投递与处置**同一事务**；
- **为什么要说明「对评价做了什么」**：举报人拿到**闭环反馈**才有持续举报的动力 —— 这是治理正循环的一环。

## 备注（架构取舍）

- **独立资源、独立端点**：举报与反馈各自成表——列表字段（举报内嵌被举报评价）与处置动作（受理联动隐藏）差异是结构性的，不是参数分流能表达的。
- **联动隐藏是「一次性动作」而非状态**：受理时隐藏（幂等：评价已隐藏 / 已删除 / 举报目标已删除时静默成功）；若要**恢复显示**（如误判），走 [B1 评价管理](./B1-评价管理.md) 的「恢复显示」—— 举报记录本身不持有「评价可见性」的状态。
- **评价删除不连带删举报**：`report.review_id` 置空、任务行保留——「评价已删除」是**显式表达**，不是脏数据。
- **`outcome` 是任务表的物理列**：「受理 / 不予处理」可从行本身判定；**文案只有一列**（`replyContent`），不采纳原因并入其中。
- **`handled_by` 记录处置人**：列表以 `handledByName` 呈现「处理人」。
- **不做批量处置**（与 B2 同口径，一期不做）。
