# 菜品录入流 · 交互与信息布局设计规范

> 归属：UI/UX 设计（双端设计权威）｜交付对象：Web 工程师
> 关联决策：2026-09-14 用户拍板（写入 `docs/project_spec.md` §7.15）——「食堂与档口」从独立管理页改为随菜品一起维护
> 视觉基线：`docs/project_spec.md` §4（Apple Design UI 规范）+ `web/src/styles/variables.css` token
> 落盘时间：2026-09-14

---

## 0. 目标

1. **口径统一**：食堂 / 档口是「菜品」的附属维度，不是需要独立经营的实体（用户原话：档口和食堂都是菜品的附属字段）。信息架构必须让维护者「编菜品时顺手维护归属」，而不是「先去另一个模块建食堂」。
2. **零跳转录入**：维护者能在一个弹窗内完成「选食堂 → 选档口（或新建档口）→ 保存菜品」全流程，无跨页跳转、无数据丢失。
3. **心智收敛**：删除「食堂（含档口）」独立管理页，避免「食堂是独立实体」的错误心智；首页配置与菜品为内容管理仅存的两张卡。
4. **一致性**：所有新增/编辑交互严格复用后台既有 `FormDialog` / `DataTable` / `ImageUpload` / `ConfirmDialog` 与 toast 反馈模式，视觉 token 全走变量，禁裸 hex。

## 1. 结论（逐项）

### 1.1 内容管理页收敛：三卡 → **两卡（菜品 / 首页配置）**，食堂**不保留只读页**

**结论**：删除「食堂」卡与 `CanteensView` 入口，`ContentManageView` 仅保留 **菜品** 与 **首页配置** 两卡。档口的改名/图片/楼层/状态等低频维护信息，收敛到菜品表单内「新增档口」小弹窗中完成；食堂不再有任何独立 UI 入口。

**理由**：
- **心智模型一致**：保留只读页会让维护者仍以为「食堂是一级实体」，与拍板口径（附属字段）冲突；只读页还会诱发「为什么这里不能改」的困惑。
- **信息架构收敛**：7 食堂 / 14 档口的量级，独立页面维护成本（进入 → 定位 → 编辑 → 返回）远高于「录菜品时顺手建」。
- **代价与对冲**：代价是「批量改档口图片/状态」无批量入口。当前量级（14 档口）下该场景频次极低（< 每周 1 次），且可通过在菜品表单的档口选择器中改单条覆盖；如未来档口数 > 40 或出现批量维护需求，再评估以「档口一览」只读页回流（届时另开设计任务）。**本期不预留半成品入口。**

> 备注：`ContentManageView.vue` 的 `sections` 数组移除 `canteen` 项，`ACTIVE_KEYS` 由 `['canteen','dish','home']` 收敛为 `['dish','home']`，默认 `activeKey` 改为 `'dish'`；`?tab=canteen` 深链需降级到 `'dish'`（不得白屏）。

### 1.2 菜品表单归属选择：**两级联动（食堂 → 档口）**，不做单级前缀分组

**结论**：菜品表单「所属归属」区采用**两级联动**：
- 第一级：**食堂** 下拉（默认空，占位「选择食堂」）。
- 第二级：**档口** 下拉（**依赖食堂**，未选食堂时 disabled + 占位「请先选择食堂」）。

**为什么不是「档口单级 + 食堂前缀分组」**：
- 现有实现 `DishManageView.vue:54-59` 把食堂名塞进档口 label（`档口名（食堂名）`），是**单级平铺**方案的现状。问题：14 档口尚可读，但下拉项文本冗长、食堂与档口的**层级关系不可感知**（用户无法「只筛某食堂的档口」），且食堂一旦增到 10+ 会迅速失控。
- 两级联动把「食堂 → 档口」的**真实数据层级**直接映射到交互层级，新用户一眼理解「档口属于食堂」，且每级选项数都小（食堂 7 / 每食堂平均 2 档口），无需滚动。

**是否需要搜索/筛选**：**不需要**。
- 量级判断：食堂 7 个、单食堂下档口 ≤ 3 个（14 / 7 均值 2），两级下拉展开即一屏可见，加搜索框属于过度设计（还占表单高度、增加视觉噪音）。
- **触发阈值（未来回流条件）**：当**单食堂下档口数 > 12** 或**食堂总数 > 15** 时，在档口下拉内启用 `filterable`（Element Plus 搜索）——本期不实现，仅作为后续评估锚点。

**必填与默认值规则**：
| 场景 | 食堂默认值 | 档口默认值 | 必填 |
|---|---|---|---|
| 新增菜品（从菜品管理页「新增菜品」） | 空（占位「选择食堂」） | 空，disabled 直到选定食堂 | 均必填 |
| 新增菜品（若有 `defaultStallId`，如从某档口下拉先导） | 由 `defaultStallId` **反查**出该档口 `canteen_id` 预选 | 预选 `defaultStallId` | 均必填 |
| 编辑菜品 | 由 `dish.stall_id` **反查**档口 → 预选其 `canteen_id` | 预选 `dish.stall_id` | 均必填 |
| 编辑时改选食堂 | 切换食堂 **清空档口**，档口下拉重新按新食堂过滤 | 需重选 | 均必填 |

**关键交互约束（防脏数据）**：
- 切换食堂**必须清空**已选档口（避免 A 食堂档口挂在 B 食堂下）。若切换前档口已有值，**直接静默清空并置回占位**，不弹确认（此时通常还没保存，且档口选择是廉价操作）。
- 档口选项**必须**按 `stall.canteen_id === 所选食堂 id` 过滤；`store.stalls` 为空或该食堂下无档口时，档口下拉置空并显示底部内联提示「该食堂暂无档口，点下方新增」（见 §1.3）。
- 保存 payload 仍只提交 `stall_id`（`DishFormDialog` 现有 `form.stallId` → `stall_id`），**不新增食堂字段**（食堂是档口的父级，由 `stall.canteen_id` 隐式决定，后端契约不变）。

### 1.3 「新增食堂 / 新增档口」内联入口：**档口选择器底部「+ 新增档口」项 → 独立小弹窗**；新增食堂走**菜品表单内联小弹窗**

**结论**：两种形态，均**不离开菜品弹窗**：

**(A) 新增档口 —— 主路径（高频）**
- 入口：**档口选择器（自定义下拉面板）底部固定一项** `+ 新增档口`，视觉为带 `·` 前缀的主色文字项，与选项列表用 1px 分隔线隔开（sticky 在面板底部）。
  - ⚠️ 实现前提：原生 `<select>` **无法**承载底部自定义项，必须把「档口」控件从 `<select>` 换成**自定义下拉面板**（见 §4 组件复用；不得引入 Element Plus `el-select` 的默认样式覆盖问题——用 `el-select` + `el-option` 无法放底部按钮项，故采用 **`el-popover` + 自绘列表面板**，或复用既有 `FilterSelect` 的交互外壳）。
- 点击后：**就地弹出第二层小弹窗**（`FormDialog`，宽 480，标题「新增档口」，`confirmText="创建并选中"`），叠在菜品弹窗之上（z-index 更高，Modal 已支持嵌套）。
- 创建成功后：**自动关闭小弹窗 → 将该新档口加入档口选项 → 自动选中它 → 食堂级联到其所属食堂**；菜品弹窗**保持打开**，其余已填字段（名称/价格/图片等）**不丢失**。
- 小弹窗**必填**：食堂、档口名称。**选填**：楼层、窗口号、位置、图片、描述。
  - 食堂字段：**预选为菜品表单当前已选食堂**；若菜品表单尚未选食堂，则该字段为空必填（用户在此新建食堂则走 (B) 的内联新建）。
  - 食堂字段旁提供**「+ 新建食堂」**小文字链，点击**再叠一层食堂小弹窗**（或用同一弹窗的「切换新建」模式，见 §3 流程说明）；推荐**复用 (B) 的食堂小弹窗组件**，避免两套。
- 新建档口的 `status` 默认 `active`（`open`），`sort_order` 默认 `0`（可选字段不在小弹窗暴露，保持极简）。

**(B) 新增食堂 —— 次路径（低频，7 食堂已够用）**
- 入口：**食堂选择器面板底部固定一项** `+ 新增食堂`（形态同 (A)）。
- 点击后弹出小弹窗（`FormDialog`，宽 520，标题「新增食堂」，`confirmText="创建并选中"`）。
- **必填**：食堂名称。**选填**：位置、描述、图片。
  > 注：现有 `CanteensView.vue:57-58` 校验 `location` 必填，但那是**独立管理页**口径。随拍板收敛为「附属字段」后，食堂仅用于分组，**名称必填即可**，位置/描述/图片降级为选填（避免录入摩擦）。此调整需 Web 工程师在新建的小弹窗内实现，**不影响** `canteenToApi` 契约（`compactPayload` 已允许多字段缺省）。
- 创建成功后：**自动关闭小弹窗 → 食堂选项追加新食堂 → 自动选中 → 档口下拉清空并启用（等待用户选/建档口）**。

**为什么不选「内联展开小表单」**：菜品弹窗已有 10+ 字段，内联再展开 5 个字段会让弹窗高度暴涨、滚动定位复杂，且与「新增档口」的小弹窗形态不一致。**统一用叠层小弹窗**，交互心智单一（都是「弹层里建、建完自动选中、自动回来」）。

### 1.4 交互一致性：沿用 `FormDialog` 保存 / 校验 / 反馈模式

**结论**：三层弹窗（菜品 / 档口 / 食堂）全部复用后台既有模式，**不引入新的反馈形态**。

| 环节 | 规范 | 参照实现 |
|---|---|---|
| 弹窗壳 | `FormDialog`（`show` / `title` / `width` / `confirm-text` / `confirm-loading` / `:on-confirm`），底部「取消 | 保存」右对齐 | `web/src/components/FormDialog.vue` |
| 提交中 | 按钮文案切「处理中…」+ disabled，防重复提交 | `FormDialog.vue:53-55` |
| 字段级校验 | 提交时统一 `validate()` → `formErrors` → 字段下方 `<p class="field-error">` 红字（`--color-error`）；**错误字段不做滚动聚焦**（与现有菜品弹窗一致），仅红字提示 | `DishFormDialog.vue:101-116 / 178` |
| 必填星号 | `<span class="required">*</span>`（`--color-error`） | `DishFormDialog.vue:176` |
| 成功反馈 | `toast.success('菜品已添加' / '档口已创建' / '食堂已创建')`，**关弹窗/回上层** | `DishFormDialog.vue:149-152` |
| 失败反馈 | `toast.error(e.message || '保存失败')`，**弹窗保持打开、表单数据保留、按钮恢复可点** | `DishFormDialog.vue:156-160` |

**保存失败的提示与恢复路径（必须明确文案）**：
1. **档口/食堂重名**：`toast.error('该食堂下已存在同名档口')` / `toast.error('已存在同名食堂')`（文案由后端 message 优先，前端兜底）；小弹窗**不关闭**，用户改名字段后重试。
2. **外键异常**（所选食堂被并发删除）：`toast.error('所选食堂已不存在，请重新选择')`；**关闭小弹窗 → 重载 `store.loadAll()` → 食堂下拉重置为空并清空档口**，用户重新选择。菜品主表单其余字段不受影响。
3. **菜品保存失败**（含 `stall_id` 指向已删档口）：`toast.error(e.message || '保存失败')`；菜品弹窗保持打开，归属区红字提示「所选档口已失效，请重新选择」，并触发一次 `store.loadAll()` 刷新档口选项。
4. **网络/500**：统一 `保存失败，请稍后重试`，表单保留。
> 原则：**任何失败都不丢用户已填数据**（除失效的归属选择外）。

### 1.5 存量页面处置：`CanteensView` / `CanteenDetailView` / `StallDetailView` —— **全部删除**

**结论**：
- `web/src/views/canteen/CanteensView.vue` → **删除**（入口 `ContentManageView` 的「食堂」卡一并移除）。
- `web/src/views/canteen/CanteenDetailView.vue` → **删除**（下钻路径随入口消失而失效）。
- `web/src/views/canteen/StallDetailView.vue` → **删除**（同上；其档口编辑能力由菜品表单内「新增/编辑档口」小弹窗承接）。
- 路由与引用清理：删除对应 `router` 条目（`/dashboard/canteens/:id` 等）与 `CanteensView` 内 `enterCanteen` 跳转；`DishDetailView.vue` 若含「跳档口详情」入口，改为**无跳转**（档口名仅作文本展示）或指向菜品编辑弹窗的归属区。

> **不做「保留但去掉编辑入口」**：保留只读页会残留「食堂是实体」的心智与死代码维护成本，且无任何只读信息是菜品表单里看不到的。**删除更干净。**

**范围外提示（交技术负责人/Web 工程师确认）**：`DishDetailView.vue` 的独立「编辑菜品」路径（现有 `confirmEdit`）若与本次归属区改动冲突，应统一收敛到 `DishFormDialog` 单一实现，避免出现两套归属选择 UI。**本规范只定义 `DishFormDialog` 为唯一归属选择实现**。

## 2. 交互流程（步骤化）

### 流程 A：新增菜品（主流程，含零跳转建档口）

1. 菜品管理页点「新增菜品」→ 打开 `DishFormDialog`（标题「新增菜品」）。
2. 归属区显示两个控件：**食堂**（占位「选择食堂」）、**档口**（disabled，占位「请先选择食堂」）。
3. 点「食堂」→ 展开下拉面板（选项=全部食堂，底部固定 `+ 新增食堂`）。
   - **分支 A1（食堂已存在）**：点选某食堂 → 面板收起 → 档口控件 enable，占位「选择档口」。
   - **分支 A2（需新建食堂）**：点 `+ 新增食堂` → 叠层食堂小弹窗 → 填名称（必填）→ 点「创建并选中」→ 成功后小弹窗关闭 → 食堂控件选中新食堂 → 档口 enable。
4. 点「档口」→ 展开下拉面板（选项=该食堂下的档口，底部固定 `+ 新增档口`）。
   - **分支 A3（档口已存在）**：点选档口 → 收起，归属完成。
   - **分支 A4（需新建档口）**：点 `+ 新增档口` → 叠层档口小弹窗（食堂预选为步骤 3 所选）→ 填档口名（必填），楼层/窗口/位置/图片/描述选填 → 点「创建并选中」→ 成功后小弹窗关闭 → 档口控件自动选中新档口，食堂保持不变。
5. 继续填写名称/价格/图片等其余字段 → 点「保存」。
6. 成功：`toast.success('菜品已添加')` + 关闭菜品弹窗 + 列表刷新（`emit('saved')`）。
7. 失败：见 §1.4，弹窗保留。

> **关键不变量**：步骤 3/4 建完实体后，**菜品弹窗始终未关闭**，所有已填字段保留。

### 流程 B：编辑菜品（归属回显 + 允许改选）

1. 列表点「编辑」→ 打开 `DishFormDialog`（标题「编辑菜品」）。
2. 按 `editingId` 取 dish → 由 `dish.stall_id` 反查档口 → 反查其 `canteen_id`。
3. 食堂控件**预选**该 `canteen_id`；档口控件**预选** `dish.stall_id`，选项列表限定为该食堂。
4. 用户改选食堂 → **档口立即清空**并重新过滤选项 → 需重选档口后方可保存（未选时保存报「请选择所属档口」）。
5. 保存/失败路径同流程 A 步骤 6/7。

### 流程 C：切换食堂时的清理（防脏数据）

1. 档口已有值 `S_a`（属食堂 `C_a`）。
2. 用户把食堂从 `C_a` 改为 `C_b`。
3. 立即执行：`form.stallId = ''`，档口下拉选项重算为 `C_b` 下档口，档口占位回「选择档口」。
4. 若 `C_b` 下无档口：档口下拉置空 + 面板内显示内联提示「该食堂暂无档口」+ 底部 `+ 新增档口` 仍可用。

## 3. 字段与校验表

### 3.1 菜品表单「归属区」（改 `DishFormDialog.vue`）

| 字段 | 控件 | 必填 | 默认值 | 校验文案 | 备注 |
|---|---|---|---|---|---|
| 所属食堂 | 自定义下拉面板（`el-popover` + 自绘列表） | 是 | 新增=空；编辑=由 `stall.canteen_id` 反查 | `请选择所属食堂` | 仅用于级联过滤，**不进 payload** |
| 所属档口 | 自定义下拉面板（同上，依赖食堂） | 是 | 新增=`defaultStallId`（并级联其食堂）；编辑=`dish.stall_id` | `请选择所属档口` | 提交仍为 `stall_id: Number(form.stallId)` |
| 档口面板底部项 | 固定 `+ 新增档口` | — | — | — | 点击开档口小弹窗；无档口时亦可点 |
| 食堂面板底部项 | 固定 `+ 新增食堂` | — | — | — | 点击开食堂小弹窗 |

**布局**：归属区两控件并排一行（`df-row`，各 `flex-1`），置于「菜品名称」同行或紧随其后；**保持在弹窗上半屏**（归属是录菜第一步心智），不放到表单底部。
> 现有实现「所属档口」在首行右侧窄列（`width:180px`，`DishFormDialog.vue:180`）；改为两控件 `flex-1` 等宽，首行改为「菜品名称 / 所属食堂 / 所属档口」三列会过窄（640 宽弹窗下每列 < 200），**建议**：第一行「菜品名称」（`flex-1`）+ 「所属食堂」（`flex-1`），第二行「所属档口」（`flex-1`）+ 其余顺延。以实际渲染不换行为准。

## 4. 复用的既有组件 / token

### 4.1 组件（**复用优先，禁重复造轮子**）

| 用途 | 复用组件 | 文件 |
|---|---|---|
| 菜品/档口/食堂弹窗壳、底部按钮、提交 loading | `FormDialog` | `web/src/components/FormDialog.vue` |

| 档口/食堂图片上传（≤3 张） | `ImageUpload` | `web/src/components/ImageUpload.vue` |
| 删除等破坏性二次确认（仅菜品删除用；档口/食堂本期无删除入口） | `ConfirmDialog`（经 `useConfirmStore`） | `web/src/components/ConfirmDialog.vue` |
| 菜品列表（列/排序/分页/三态） | `DataTable` | `web/src/components/DataTable.vue` |

| 搜索输入 | 约定用 `el-input` | 见项目既有约定 |

**新增控件（下拉面板）实现约束**：
- 需要「底部固定新增项」的下拉，**不可用原生 `<select>`**（无法承载自定义底部项），也**不建议 `el-select`**（`el-option` 列表内插槽无法自然固定在面板底部）。
- **推荐**：基于 **`el-popover`**（或既有 `FilterSelect` 的交互外壳）自绘列表面板：选项区（可滚动，`max-height` 约 240px）+ 1px 分隔线（`--border-light`）+ 底部固定 `+ 新增档口` 项（主色文字、hover `--color-primary-bg`、键盘可聚焦）。
- 面板需支持：点外部关闭、Esc 关闭、选中后关闭、`aria-haspopup="listbox"` / `role="listbox"` / 选项 `role="option"`（可访问性）。
- 控件视觉与既有表单控件（`input`/`select`）**高度与圆角一致**（`--radius`、内边距对齐），占位文案灰色（`--text-light`），已选值深色（`--text-primary`）。

## 5. 验收要点（供质量门禁逐条核对）

**A. 内容管理页收敛**
1. `ContentManageView` 仅显示「菜品」「首页配置」两卡，无「食堂」卡。
2. 深链 `?tab=canteen` 不白屏，降级到「菜品」。
3. 仓库中不再存在 `CanteensView.vue` / `CanteenDetailView.vue` / `StallDetailView.vue` 及其路由引用、import、跳转死链（全库搜 `CanteensView`、`CanteenDetailView`、`StallDetailView`、`/dashboard/canteens` 应 0 命中，除本设计文档/变更记录）。

**B. 菜品表单归属**
4. 新增菜品：食堂/档口均为空；**档口在选定食堂前 disabled**（可见但不可交互，非隐藏）。
5. 选择食堂后，档口下拉**只列该食堂的档口**（不出现其他食堂档口）。
6. **切换食堂后档口被清空**，需重选才能保存（验证无跨食堂脏数据）。
7. 编辑菜品：食堂/档口**正确回显**（档口反查食堂成功，食堂不在档口选项过滤前为空）。
8. 未选档口点保存 → 红字 `请选择所属档口`，弹窗不关。

**C. 内联新增实体（核心）**
9. **「菜品表单可在不离开弹窗的情况下新建档口并选中」**：点档口面板底部 `+ 新增档口` → 小弹窗 → 只填食堂+档口名 → 点「创建并选中」→ 小弹窗关闭 → 档口控件显示新档口名且已选中 → 菜品弹窗仍开、已填字段（名称/价格/图片）**未丢失**。
10. 新增档口时其「所属食堂」**预选**为菜品表单已选食堂。
11. 同理验证 `+ 新增食堂`：新建后食堂自动选中、档口 enable 并清空。
12. 小弹窗必填校验：食堂/档口名留空 → 对应红字，不提交。

**D. 数据正确性**
13. **菜品保存后归属正确**：新建档口后保存的菜品，其 `stall_id` = 新档口 id；列表「所属档口」列显示新档口名；小程序端 / 后端查该菜品的 `stall.canteen_id` 指向所选食堂。
14. 档口/食堂创建后，其 `status` 为 `active`（前端 `open`），在菜品归属选择中**可被选中**（不被过滤掉）。

**E. 一致性 / 失败恢复**
15. 三层弹窗均复用 `FormDialog`，按钮为「取消 | 保存/创建并选中」，提交中显示「处理中…」并 disabled。
16. 档口重名：`toast.error` 提示 + 小弹窗不关闭 + 数据保留。
17. 菜品保存失败（如档口已失效）：弹窗保留 + 红字提示 + `store.loadAll()` 刷新选项。

**F. 视觉规范**
18. 全库新增/改动代码无裸 hex（搜 `#` + 6 位 hex 于本次改动文件），无裸 `0.97`（按压统一 `var(--press-scale)`），圆角/间距/字号走 token。
19. 下拉面板键盘可达（Tab 聚焦、Enter 选中、Esc 关闭）、有 `role`/`aria-*` 基本标注。
20. 弹窗叠层 z-index 正确（小弹窗在菜品弹窗之上，遮罩不串层），关闭小弹窗后菜品弹窗可继续操作。
