## 缺失的业务原则

> 后端视角下、当前代码「无规则可依」的领域清单。每条一句话，供制定「业务原则 + 产品蓝图」时逐条拍板。

1. **写入值域原则**：所有面向管理端的枚举/标签类字段（`feedback.type`、`dish.tags`、`dish.spice_level`、`dish.portion`、`dish.status`、`review.sort`）必须有单一真源白名单并在此收口校验，绝不允许「DTO 声明但 Service 静默忽略」或「原样落库」。
2. **金额值域原则**：以「分」为单位只是量纲约定，还须补值域约束（正数、促销价 ≤ 原价），金额字段的非法组合必须在 Service 拒绝而非落库。
3. **字段生命周期原则**：任何字段的「引入」与「下线」都须成对处置——端上零消费且后端从不写入的字段（`portion`、`dish_audit` 通知链路）应显式下线或显式登记为「仅存量兼容」，不得长期悬置。
4. **聚合与真实数据一致性原则**：所有冗余计数/聚合字段（`dish.avg_rating`、`rating_count`、`review.useful_count`、`dish.view_count`）必须明确「谁是真源、何时重算、失败如何补偿」，异步失败不能只有一行告警日志。
5. **评分口径原则**：须明确「内容安检不可见的评价是否计入菜品评分与评价数」，以及「菜品下架/档口关闭是否影响其评分参与度」——当前这些口径在 SQL 层各自为政（`is_hidden=0` 一处、`status='on'` 另一处）。
6. **引用完整性原则**：删除类操作（删菜品 / 删评价 / 账号合并）须成对定义级联范围（评价、`review_useful`、`view_log`、`notification`），当前三处删除的级联口径互不一致。
7. **权限归属清晰原则**：每个写接口都必须能回答「谁可以调用」，禁止出现「路径挂在学生侧、语义属管理端」的接口（`PUT /auth/password`），也禁止 Swagger 中留下「后续需要补权限边界」这类在当前权限模型下永不成立的悬空承诺。
8. **参数非法即报错原则**：过滤/排序/分页类参数应与写路径同口径做白名单校验，非法值返回 400，绝不静默降级为「另一种合法语义」或「空列表」——静默降级会掩盖真实的数据积压。
9. **无入口即无功能原则**：任何「已暴露的接口/通知类型/审核分支」都必须有可复现的触发入口；只有历史存量数据能走到的分支须显式登记，防止被误当作在用能力继续投入。
10. **共享逻辑单一实现原则**：跨模块的同一条业务契约（如 UGC 配图 ≤3 张 + 受信域名白名单）必须有且只有一份实现，重复实现等同于允许契约漂移。
