## 缺失的业务原则

1. **「表单里出现的字段必须能被提交」**——任何在 UI 渲染的输入项，其值必须经 payload 送达后端并被消费；否则等于对管理员撒谎（WEB-02 alias）。
2. **「有接口封装就必须有页面触达，否则一并删除」**——后端 + API 层 + 类型三层齐备但零入口，属半成品死链，须在当轮收敛（WEB-03/WEB-06 的判定依据）。
3. **「后端校验是唯一真相，前端不得放宽」**——凡后端 `@NotBlank`/`@Valid` 的字段，前端必须同步为必填并给同文案提示，禁止出现「选填」与实际必填并存的矛盾（WEB-01）。
4. **「跳转必须携带并消费目标态」**——带参数跳转（如 `?q=菜名`）时，目标页必须消费该参数并让用户看到筛选结果，否则视为不闭环（WEB-04）。
5. **「契约声明的返回字段必须有展示落点」**——接口返回且类型声明的关键字段（含列表/明细），要么渲染、要么显式登记「暂不消费」并给出期限（WEB-05）。
6. **「不可逆动作一律二次确认，且确认文案说明不可逆性与连带影响」**——处理反馈（不可撤回 + 立即通知学生）、删除菜品（连带评价载体）均属此类；确认标准在全站必须一致（WEB-10/WEB-15）。
7. **「多人可写同一实体时，必须有并发可感知机制」**——后台为多管理员共用同一口令，静默覆盖是不可接受的数据风险；至少需「已保存但他人可能已改动」的可感知提示（WEB-09）。
8. **「枚举展示必须与后端常量表同源」**——动作/状态/类型等枚举的下拉选项与文案必须由后端常量生成或逐条对齐，禁止前端手写子集（WEB-08）。
9. **「任何未匹配路由必须有兜底落点」**——不允许出现白屏；兜底应指向工作台并保留用户当前位置感知（WEB-07）。
10. **「审核态的展示与处置必须同时存在，或同时删除」**——展示 `audit_status`/`reject_reason` 却无处置动作，会让管理员误以为系统支持审核；两者必须同批决策（WEB-03/WEB-14）。
11. **「同一业务动作在全站的确认粒度必须统一」**——同类破坏性/通知性动作（删除、隐藏、处理）不得有的确认有的不确认（WEB-15）。
12. **「零消费的状态/派生数据不得滞留」**——`activeList` 三链、`todayOrders` 等无消费成员属死代码，与项目「不涉及下单」定位相悖，须随当轮清理（WEB-12/WEB-11）。
