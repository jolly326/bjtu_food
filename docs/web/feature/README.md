## 阅读约定

> 与学生端 feature 文档**同构**——每份文档固定为 **介绍 → 接口 → 字段（字段名 + 中文解释）→ 数据** 四段；讨论期可临时带「答疑」段，**拍板后结论并入正文、答疑清空**。
> **feature 按功能拆分**：每个功能一份独立文档、**独立自洽**，不写跨板块关联表述（页面路径 / 组件名 / 视觉口径一律不写）。
> **正文只保留最终设计形态**：不写落地状态（「待实现 / 已落地 / 当前实现为 …」一律不写）；**与现有代码不一致的条目一律集中在文末「与当前代码的差异」板块**，差异清零时该板块保留标题并写「无（文档与代码一致）」。
> ⚠️ **本目录是 web 端「完全重写」的设计稿**：编写时**不参考既有的 web 实现**（既有实现将被整体推翻）。落地顺序固定为 **文档评审通过 → 再按文档重写代码**，不得反向由代码推翻文档。
> 字段口径：字段名以**接口实况**为准（后端 Java DTO/VO 出参，统一 camelCase）；类型列的 `number / string / boolean / array / object / null` 为 JSON 侧类型。

## 通用结构（跨功能复用，只在此处定义一次）

### 统一响应信封（`Result<T>`，所有接口）

| 字段名 | 类型 | 中文解释 |
|---|---|---|
| `code` | number | 业务状态码：`200` 成功；`400` 参数 / 业务校验失败；`401` 未登录 / 令牌失效；`403` 无权限；`4001` 资源不存在；`500` 服务器异常 |
| `message` | string | 提示信息（失败时给用户看的文案） |
| `data` | T \| null | 业务载荷；写操作类接口通常为 `null` |

> **管理后台不使用 `4031`**（该码专指学生端「未完成邮箱认证」，管理端无认证态）。

### 分页结构（`PageResult<T>`）

| 字段名 | 类型 | 中文解释 |
|---|---|---|
| `records` | T[] | **当前页数据行**（消费方以此为准）；**分页壳仅此一项**；结束判据 = 本页返回条数 < 请求的 `pageSize` |

### 金额约定

**所有金额一律以「分」为单位传输**（`number`）；分↔元转换只允许在管理端的 `utils/money`，**禁止在页面 / 组件里裸算**。

### 管理端端点前缀

全部端点位于 `/admin/**`（不含学生端路径），并叠加后端 `context-path` `/api/v1`，故完整路径形如 `/api/v1/admin/dishes`。

## 与学生端的关系（治理闭环）

学生端产生数据、管理后台消费与治理，四条 UGC 链路各有明确归宿：

| 学生端产生 | 管理后台治理 | 处理结果 |
|---|---|---|
| 写评价（A-06）/ 删除（A-07） | 评价管理（B-08）：隐藏 / 恢复 / 删除 | 隐藏后学生端列表不再可见（含作者本人） |
| 意见反馈（A-10） | 意见反馈管理（B-09）：回复 / 退回 | 站内通知回执（学生端 A-11） |
| 举报评价（A-08） | 举报管理（B-10）：处置被举报对象 + 回复举报人 | 站内通知回执 |
| 菜品纠错（A-16） | 菜品纠错管理（B-11）：采纳 / 拒绝 | 采纳写回 `dish`，拒绝留存原因；均发回执 |

> **菜品主数据由管理员独占维护**：学生端**无**菜品写接口（红线），学生发现信息问题只能走反馈 / 纠错通道，由管理员在 B-05 录入或采纳。

## 改动前注意

1. 口径冲突先问技术负责人；**本目录 + `docs/client/feature/`（红线段）为现行权威**。
2. 加表 / 改字段 → 改 `server/src/main/resources/db/schema.sql`（及 seed），**不直连库**。
3. 新增接口先对齐本目录对应功能文档的契约与错误码（统一响应 / 分页结构见上「通用结构」）。
4. **本目录文档评审通过前，不得据此改动 `web/` 代码**；评审通过后按文档整体重写。
