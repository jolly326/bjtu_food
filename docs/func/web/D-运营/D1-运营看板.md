> 归属：**D 运营**
> 状态：**已定稿** —— 2026-10-02 拍板：看板 = **登录后首屏的统一待办入口**；三区分区（待办 / 主数据健康度 / 概况），每区 ≤4 项，且**必须含可点击的最近待办列表**。

## 介绍

**登录后的首屏** —— 把"今天要处理什么"和"主数据有没有该修的"一屏看完，**点击直达**对应处置页。

**定位：只读聚合页** —— 本页**不含任何写操作**；所有处置都在各自页面（[B1](../B-UGC治理/B1-评价管理.md) / [B2](../B-UGC治理/B2-意见反馈管理.md) / [B3](../B-UGC治理/B3-举报管理.md) / [B4](../B-UGC治理/B4-菜品问题反馈管理.md) / [A1~A7](../A-主数据维护/)）。它正是 "三个独立菜单 + 看板" 结构里的那个**统一入口**（见 [web/README](../README.md)）。

**为什么需要它**：反馈 / 举报 / 菜品问题反馈在 client 是**三条独立链路**，后台也按**三个菜单**分别处置 —— 单管理员场景下，**没有看板就只能逐个菜单翻**才知道今天有没有活。

**三区职责**：

| 区 | 回答的问题 |
|---|---|
| **待办** | 有多少要处理、**最近的是哪些**（可点击直达） |
| **主数据健康度** | 有哪些**该修**的脏数据 |
| **概况** | 平台规模（只读） |

## 数据（**全部只读**）

| 表 | 读什么 |
|---|---|
| `user_feedback` | 待处理反馈数 / 待处理举报数 / `recent` 里的反馈与举报项 |
| `dish_correction` | 待处理菜品问题反馈数 / `recent` 里的菜品问题反馈项 |
| `dish` | 在售菜品数 / 无图片 / 未归档口 / 无分类 |
| `stall` | 无菜品的档口数 |
| `review` | 评价总数 |
| `user` | 用户总数 / 已认证数 |

> 本页**不写任何表**。计数口径与各自列表页**同一判据**（如"在售"=`status='on'`、待办=`status='pending'`）。

## 性能与一致性

- 一次请求完成全部计数 + 1 次最近列表查询：计数走 `status` / `is_hidden` / `stall_id` / `type` 等**已有索引**；`recent` 跨三类数据源取固定条数后应用层归并（量级极小）；
- **不做缓存**：首屏要准，且单管理员访问频率极低；
- 计数是**瞬时快照**，与列表页可能存在秒级偏差 —— 可接受（点进去以列表为准）。

## 备注（架构取舍）

- **"最近 5 条待办"是必须项**：只有数字的话，看板退化成**数字墙** —— 管理员仍得逐个菜单去翻；可点击的待办列表才是它的核心价值。
- **健康度只挑"可执行的"**：无图片 / 未归档口 / 无分类 / 空档口，都是**当场能修**的；**不列**"描述为空""属性为空"这类**允许为空**的项 —— 噪音项会让整个健康度区失去意义（管理员会学会无视它）。
- **概况只给规模、不给时间序列**：趋势图要按天聚合 + 历史留存，属"运营系统"范畴；当前是**单管理员轻运营**，不做。
- **不复活操作日志**：单管理员（[C1](../C-账号与访问/C1-管理员登录与访问控制.md)）；安全审计留痕不在本页范围，本页不引入（其口径见 [`secur/web/审计与告警.md`](../../../secur/web/审计与告警.md)）。
- **每区 ≤4 项**：首屏的目标是"一眼扫完"，不是"报表"。
- **健康度的「未归档口 / 无分类」是存量清理指标**：[A3](../A-主数据维护/A3-菜品管理.md) 要求 `stallId` / 分类**录入必填**，故这两项**只会命中历史数据**（新录入不产生）—— 长期为固定值属正常，**不是 bug**。
