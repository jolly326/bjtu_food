# C2 · 用户管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](./C1-管理员登录与访问控制.md)）
> 归属：**C 账号与访问**
> **口径要点**：管理动作共四组：**启用 / 禁用**、**踢下线**、**解绑邮箱**、**删除账号（注销）**

## 介绍

治理**学生用户账号**（`user`）—— **启用 / 禁用**、**解绑认证邮箱**、**删除账号（注销）**。

**定位**：管理端只掌控「**账号能不能用 / 认证绑定 / 账号存续**」，**不代用户改资料**：

| 不做 | 原因 |
|---|---|
| 改昵称 / 头像 / 邮箱 | 属**学生自助**（[`PUT /auth/profile`](../../../api/client/auth.md) 与邮箱认证流程）；代改会绕过认证流程（尤其邮箱绑定）。管理端对邮箱只持有「**解绑**」（回落游客态），**不代绑新邮箱** —— 重新认证必须由用户本人走邮箱验证码流程 |
| 物理删除用户行 | `user` 行**永不物理删除**（删除账号为匿名化注销），否则历史评价 / 反馈会失去归属 |

**禁用的完整语义（三层，缺一不可）**：

| 层 | 行为 | 落点 |
|---|---|---|
| ① **拒新登录** | [`POST /auth/wechat-login`](../../../api/client/auth.md) → `400`「账号已被禁用」 | `AuthServiceImpl` |
| ② **已签发 token 即时失效** | 禁用时把该用户所有 token 拉黑；恢复 `active` 时解除 | `tokenBlacklist.revokeUser / restoreUser` |
| ③ **写操作实时判定** | 非 `active` 一律 `403`「账号已被禁用」（JWT 载荷不含 status，故每次实时查库） | `UserServiceImpl` |

> ⚠️ **②的黑名单是 JVM 内存态**（见 [docs/README](../../../README.md) 的「已知取舍」：单容器部署，重启清零）。**重启后存量 token 在有效期内可能仍被携带** —— 由 **③ 实时判定兜底**（**写操作必拒**）；读接口本身对游客公开，禁用用户"还能读"可忽略。

**不投递回执**（**通用"处置回执"口径的明确例外**）：
- **禁用 / 删除账号**：账号无法登录 ⇒ 看不到站内通知，发回执没有意义；
- **解绑邮箱**：端上 UGC 写被 `4031` 实时拦截并引导重新认证，用户可自助恢复，无需站内通知。

**解绑邮箱**：只置空 `bind_email`（认证态唯一判据）—— 账号**立即回落游客态**，UGC 写实时被拒；**不改 `status`、不动 `email`（账号标识）**，登录与已发表内容不受影响。

**删除账号**：与本人自注销 [`DELETE /auth/account`](../../../api/client/auth.md) **完全同口径**的匿名化注销（非物理删除），由管理端发起 —— 匿名化昵称 / 解绑 openid 与邮箱、删除站内通知、拉黑该 userId 全部 token；终态保护（已注销 / 已禁用均拒绝）与本人一致。

| `user` | 读写账号状态（启用 / 禁用）；解绑写 `bind_email = NULL`；注销匿名化写昵称 / `username` / `avatar` / `email` / `openid` / `bind_email` / `status` | 账号状态 / 认证绑定 / 匿名化 |

## 与当前代码的差异

> 本节集中登记与现有代码的差异；清零即写「无」。

- **`updatedAt` 出参**：表已有 `updated_at` 列，无需 DDL。
- **`keyword` 筛选**：[`GET /admin/users`](../../../api/web/users.md) 支持 `keyword`（昵称 / 账号 / 绑定邮箱三路模糊匹配），可按人定位。
- **`status` 只接受 `active` / `disabled`**：Service 枚举校验（传 `deleted` → `400`）。
- **禁用联动 token 黑名单**：`revokeUser` / `restoreUser` 实现禁用的三层语义（重启清零 + 写侧兜底）。
- **踢下线与禁用分开**：`POST /admin/users/{id}/kick` 只让该 userId 已签发的 token 立即失效，**不改账号任何列** —— 用于「token 被滥用但账号本身无过错」的止损（禁用的代价是用户完全用不了）。
- **解绑邮箱联动吊销 token**：解绑改变账号能力边界（认证态由 `bind_email` 派生），故同时吊销该 userId 既有 token，端上静默登录换发新 token。
- **不做禁用回执**：禁用无回执 —— 与通用「处置回执」口径的例外（用户无法登录，看不到）。

## 备注（架构取舍）

- **禁用必须"三层齐备"**：只拦新登录 ⇒ 已登录的封禁对象还能继续写；只拉黑 token ⇒ 重启后又放行。**① 拦登录 + ② 拉黑 token + ③ 写侧实时判定**三者叠加，才在"内存态黑名单 + 单容器"的既有架构下拿到足够强的效果。
- **删除账号 = 匿名化，不是销毁**：注销会匿名化昵称、解绑 openid / 邮箱（**不可逆**），但 `user` 行保留（历史内容归属不丢）；与本人自注销共用同一服务端实现与 **`UserStateWriteLock`** 临界区 —— 管理员启停 / 代注销 / 本人注销对同一账号的写互不交错，终态由最后一个临界区决定。
- **解绑邮箱只动 `bind_email`**：认证态不进 JWT，按列实时查库判定 ⇒ 置空即时生效；重绑必须走本人验证码流程，管理端不代绑（否则绕过「持有人 = 本人」的认证前提）。
- **不代改资料**：昵称 / 头像 / 邮箱是**学生自助**能力，管理端代改会绕过认证流程（尤其邮箱绑定）。
- **不做用户维度统计**：本页是「账号治理」；概况与待办聚合在 [D1 运营看板](../D-运营/D1-运营看板.md)。
- **有行内详情抽屉（只读）**：字段全览（账号 / 昵称 / 头像 / 状态 / 微信绑定 / 认证邮箱 / 时间）+ `禁用·启用` / `解绑邮箱` / `注销账号` —— 这是「编辑 / 删除类动作一律进详情」的统一形态（见 [列表页模板 §C2](../../../ui/web/列表页模板.md)）；🔴 **管理端不代改资料**，故抽屉内**无编辑表单**（昵称 / 头像由用户本人维护）。
