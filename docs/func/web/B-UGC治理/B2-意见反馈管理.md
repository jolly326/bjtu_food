# B2 · 意见反馈管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**B UGC 治理**
> **口径要点**：`handled` 的 `reply` **可选**（无则回执用固定文案），`rejected` 的 `rejectReason` **必填**；与举报**共用表与端点、按 `category` 分流**；**不做批量处理**。

## 介绍

处理学生提交的**纯意见反馈**（`user_feedback` 中**非举报**的行）—— 类型由学生端写入白名单限定为 `bug` / `suggestion` / `other`，页面类型下拉**只列这三类**（口径见 [schema/user_feedback.md「写入类型白名单」](../../../schema/user_feedback.md)）。

**动作恰好两个**：**回复并通过（`handled`）** 或 **不采纳 / 退回（`rejected`）**；处理结果向提交人投递**站内回执**（对齐 [web/README](../README.md) 的「处置回执」口径）。

**职责边界**：

- **举报（`type='report'`）不在本页** —— 走 [B3 举报管理](./B3-举报管理.md)；**同一张表、同一个处理端点**，两页**按 `category` 分流**；
- 本页**不碰**评价（B1）、菜品（A3）、菜品问题反馈（B4）等被处置对象。

**为什么与举报共用**：`user_feedback` **一表两用**（见 [schema/user_feedback.md](../../../schema/user_feedback.md) 的「一表承载两类数据」）——两类数据的**处理流程完全相同**（提交 → 管理员处理 → 回执），拆表 / 拆端点会把整套逻辑复制一份。

## 接口

端点 / 入参 / 出参 / 错误码见 [**api/web/feedback.md**](../../../api/web/feedback.md)（意见反馈与举报共用契约唯一真源）。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `user_feedback` | 读写 `status` / `reply` / `reject_reason` / `handled_at` | 反馈本体 |
| `notification` | **写**（处理回执） | 站内回执 |

> 列口径见 [schema/user_feedback.md](../../../schema/user_feedback.md)。处理动作**不改** `type` / `sub` / `content` 等原始内容。

## 回执文案

| 结论 | 标题 | 正文 |
|---|---|---|
| `handled` | 反馈已处理 | `你提交的反馈已处理` + （有 `reply` 时）`：<reply>` |
| `rejected` | 反馈未采纳 | `你提交的反馈未采纳：<rejectReason>。` + （有 `reply` 时）`处理说明：<reply>` |

- **投递口径** —— 判据为 `user_id > 0`：**静默登录的游客有 `userId`，同样收到**；**匿名提交（`user_id = 0`）不投递**；
- **投递失败不阻塞**处置（独立 try）。

## 与当前代码的差异

> 本节集中登记与现有代码的差异；清零即写「无」。

- **`reply` 为条件可选**：仅 `rejected` 时必填 `rejectReason`；`handled` 允许无回复，回执正文退化为固定结论文案（护栏：回执内容不得为空、不得以「：」结尾，杜绝空通知）。
- **新增 `category` 筛选参数**：[`GET /admin/feedbacks?category=feedback|report`](../../../api/web/feedback.md)（`feedback` = 排除 `type='report'`；`report` = 仅举报；不传 = 全部）。
- **`updatedAt` 出参**：表已有 `updated_at` 列，无需 DDL。
- **`FeedbackAdminVO.type` / `sub` 语义见 [api/web/feedback.md](../../../api/web/feedback.md)**（写入白名单为 `bug` / `suggestion` / `other`）。
- **不做批量处理**（单条处理已覆盖当前量级，留作演进）。

## 备注（架构取舍）

- **`handled` 可无回复、`rejected` 必须有原因**：这是"通知不失语"与"不逼人说废话"的平衡点。
- **与举报共用表与端点**：合表理由见 [schema/user_feedback.md](../../../schema/user_feedback.md)；**分流只发生在列表参数**（`category`），处理逻辑完全复用。
- **`outcome` 不落物理列**：由 `status` + `reject_reason` 派生（`rejected ⇒ reject_reason 非空`；`handled ⇒ reject_reason 为 NULL`），避免新增列与状态不一致。
- **不记操作人**：管理端为单管理员。
