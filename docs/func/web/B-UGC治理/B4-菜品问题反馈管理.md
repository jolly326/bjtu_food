# B4 · 菜品问题反馈管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**B UGC 治理**
> 状态：**已定稿** —— 2026-10-02 拍板：**只对比「仍有差异」的项**并**逐项确认（部分采纳）**；采纳前给出**原值 → 新值对照**；`floor` 改动须提示**连带影响**。
> 处置对象新增 `type=gone`（已经下架），**按 `type` 分派不同动作**（依据：内容供给与维护闭环——下架反馈天然含误报，须人工逐项确认，避免一次误报即永久删除菜品全部历史评价）。

## 介绍

处理学生提交的**菜品问题反馈**（`dish_correction`）—— **两类**，**按 `type` 分派不同动作**：

| `type` | 语义 | 用户提交形态 | 处置动作 |
|---|---|---|---|
| **`field`** | **信息有误** | **改动项快照**（未改动列留 NULL） | **逐项核对 → 采纳（部分可选）或拒绝** |
| **`gone`** | **已经下架** | **一键提交**（各差异项列恒 NULL），说明与图片**选填** | 🔴 **仅「下架」或「拒绝」** —— **不得删除** |

结果均向提交人投递**站内回执**。

### 🔴 红线：`gone` 处置**不得提供「删除」**

| 操作 | 语义 | 数据层 | 评价 | 可逆 |
|---|---|---|---|---|
| **下架** | 暂时不在售 | `status=off` | **保留** | ✅ **可重新上架** |
| **删除** | 彻底移除 | **物理删除** | 🔴 **级联删除**（`ON DELETE CASCADE`） | ❌ **不可逆** |

> **`gone` 反馈天然含误报**（用户可能看错窗口、菜品只是临时售罄）。若此界面提供「删除」，则「**一次误报 + 一次点错 = 该菜全部历史评价永久消失**」。
>
> ⇒ **删除只允许在 [A3 菜品管理](../A-主数据维护/A3-菜品管理.md) 由管理员主动执行**（带二次确认，明示「将一并删除 N 条评价」）；**本界面不出现「删除」按钮**。

### ⚠️ 无「下架阈值」：`≥1 条即进待办，是否下架由人工决定

| 环节 | 规则 |
|---|---|
| **进入待办队列** | **≥1 条即进**（按 `user_id + dish_id` 去重后）—— 去重是**防单人刷队列**，**不是决策门槛** |
| **是否下架** | **管理员人工决定**；系统**不自动下架** |
| **驳回** | 必填 `reject_reason`，回执告知用户「经核实仍在售」 |

> **依据**：进队列 ≠ 自动下架；管理员看到的是「有人反馈 + 可选说明/图片」，判断成本本就很低。设门槛只会让**用户的反馈石沉大海**。

## 处置流程（按 `type` 分派）

```
列表（api/web/corrections.md）
        ↓
   ┌────────────────────────────┐
   │ 按 type 分派                │
   └───┬────────────────────┬───┘
       │                    │
  field（信息有误）      gone（已经下架）
       │                    │
  差异对照 + 逐项勾选     「N 人反馈已下架」
       │                    │
  ┌────┴────┐          ┌───┴────┐
  │ 采纳     │          │ 下架   │
  └────┬────┘          └───┬────┘
       │                    │
  写回 dish/stall      dish.status=off
  （不删除）           （可重新上架）
       └────────┬───────────┘
                ↓
          站内回执投递
```

**动作恰好两个**：**采纳**（把选中的差异项写回菜品）或 **拒绝**（不采纳，必填原因）；结果向提交人投递**站内回执**。

**`field` 型反馈范围（七项）**：名称 / 现价（分）/ 食堂 / 档口 / 楼层 / 属性 / 图片（**≤5 张**）；字段清单见 [api/web/corrections.md](../../../api/web/corrections.md)。

- **不含菜品种类**（`meal_type_id`）—— 种类是**系统维度取值**、由管理员在 A3 直接改，不在反馈范围（client 反馈页也没有该字段）；
- **不纠正原价** —— 原价随促销波动、属运营口径（见 [client B6](../../client/B-UGC表达与治理/B6-菜品问题反馈.md)）。

**关键连带影响**（`field` 型）：`floor` 是**档口的场所属性**（菜品无楼层字段）⇒ 采纳 `floor` 会**写回目标档口**并**同档口其他菜品一并生效**，故必须在采纳前明确提示。
**`gone` 型无差异项可采纳** —— 处置只有两个动作：**下架**（置 `dish.status=off`）或 **拒绝**（必填原因）。

**职责边界**：只管反馈记录与采纳写回；**菜品本体编辑**在 [A3 菜品管理](../A-主数据维护/A3-菜品管理.md)，**属性取值字典**在 [A4](../A-主数据维护/A4-菜品属性维度管理.md)。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `dish_correction` | 读（类型 / 说明 / 图片）；读写（处置状态 / 回复 / 不采纳原因 / 处理时间） | 问题反馈本体 |
| `dish` | **读**（原值对照 + 菜名）；**写**（`field` 采纳的字段，楼层除外；**`gone` 处置置为下架**） | 目标菜品 |
| `stall` | **读**（档口匹配 / 候选）；**写**楼层（**连带同档口其他菜品**） | 归属档口 |
| `dish_attribute_dimension` / `dish_attribute_value` | **读**（维度校验）；**写**（**登记新取值**：采纳的中文未命中字典则新建，见 [A4](../A-主数据维护/A4-菜品属性维度管理.md)） | 属性维度与取值字典 |
| `notification` | **写**（处理回执） | 站内回执 |
| `user` | **只读**（提交人昵称） | 提交人 |

> **属性采纳的存储口径**：快照里的属性是**中文**（用户提交原样），采纳时按「维度 + 中文」查取值字典（命中即用、**未命中新建**）解析为**取值 ID** 后写入 `dish.attributes` —— 见 [schema/dish_correction.md](../../../schema/dish_correction.md) 与 [A4](../A-主数据维护/A4-菜品属性维度管理.md)。
> **`images` 采纳的地址口径（必须转换）**：菜品问题反馈快照存的是**绝对 URL**，而 `dish.images` 是**相对路径列**（[schema/dish.md](../../../schema/dish.md)）⇒ 采纳写入前**必须把绝对 URL 还原为站内相对路径**（取 path 入库），否则同一列混存两种形态、出参二次拼域名导致**详情页图片 404**。
>
> ⚠️ **属性采纳必须「按维度合并」，SHALL NOT 整体覆盖**（否则会静默抹掉其他维度）：菜品问题反馈快照**只含改动维度**，因此采纳时 =
> ① `dish.attributes` **现有键全部保留**；② 只对本次**勾选采纳**的维度写入解析后的取值 ID；③ 勾选采纳且提交值为**空数组**（用户清空该维度）⇒ **删除该键**（该维度置空），**SHALL NOT 落空数组**（破坏 `single` = 字符串 / `multi` = 数组的形态）。

## 回执文案

| 结论 | 标题 | 正文 |
|---|---|---|
| 采纳（全部项） | 菜品信息已更新 | `你提交的菜品信息纠错已采纳，菜品信息已更新` + （有 `reply` 时）`：<reply>` |
| 采纳（**部分项**） | 菜品信息已更新 | `你提交的菜品信息纠错已采纳：<已采纳字段中文名>` + （有未采纳项时）`；未采纳：<未采纳字段中文名>` + （有 `reply` 时）`。处理说明：<reply>` |
| 拒绝（`field`） | 菜品信息未采纳 | `你提交的菜品信息未采纳：<rejectReason>` + （有 `reply` 时）`。处理说明：<reply>` |
| **下架**（`gone` 采纳） | 菜品已下架 | `你反馈的菜品已下架，感谢反馈` + （有 `reply` 时）`。处理说明：<reply>` |
| **拒绝**（`gone`） | 菜品仍在售 | `经核实，该菜品仍在售：<rejectReason>` + （有 `reply` 时）`。处理说明：<reply>` |

- **部分采纳必须逐项告知**：用户提交了 3 项、只采纳 2 项时，他需要知道**哪一项没被采纳**，否则会重复提交；
- **投递口径**：判据 **`userId` 有效**（**静默登录的游客亦有 userId ⇒ 投递**；匿名提交无归属，不投递）—— 见 [web/README](../README.md) 的「处置回执」；
- **投递失败不阻塞**处置。

## 与当前代码的差异

**无（文档与代码一致）**

> **实现要点**（供实现与评审对照）：
>
> - **差异对照**：[`GET /admin/corrections/{id}`](../../../api/web/corrections.md) **只返回仍有差异的项**（原值取实时值；楼层项标记**会连带影响同档口其他菜品**；目标菜品已物理删除时为空列表）—— **出参结构以契约为准**。差异对照以「方法 + 路径」双维护栏锁死（避免只比路径而漏判方法差异）。
- **逐项采纳**：`acceptedFields`（必填非空，空数组 `400`），只写回选中项；不变量——**采纳项必须是「此刻仍有差异」的项**（否则 `400`）、**两段式档口确认仅在采纳了 `canteenName`/`stallName` 项时触发**（只改楼层时不触发档口确认）。
- **拒绝的 `reply` 为可选**：`DishCorrectionHandleReq.reply` 无 `@NotBlank`（仅 `rejectReason` 必填）；`reply` 留空时回执正文退化为「不采纳原因」，保证提交人始终收到可读内容（对齐 [B2](./B2-意见反馈管理.md)）。
- **采纳支持可选附注**：`DishCorrectionAdoptReq.reply`（≤600），缺省仍用固定文案「已采纳，菜品信息已更新」。
- **回执口径（登录级）**：`sendCorrectionReceipt` 判据为「提交时带 `userId` 即投递」（不按邮箱认证过滤），与 B1 / B2 / B3 一致。
- **列表支持按菜品筛选**，并新增「差异项数 / 楼层影响面」摘要字段（列表快照不展开全字段）—— 字段清单见 [api/web/corrections.md](../../../api/web/corrections.md)。
- **`DishCorrectionAdminVO.attributes` 语义**：快照键 = 维度 ID（与 `dish.attributes` 键形态一致）、值存**中文**（采纳时解析为取值 ID）。
- **口径**：两段式档口确认、`status=pending` 才可处理的幂等、目标菜品已删除返回 `4001`。

## 备注（架构取舍）

- **只列"仍有差异"的项**：采纳清单必须反映**此刻**的事实，而不是提交当时的事实 —— 否则会出现"采纳一个和当前值一样的值"。
- **`acceptedFields` 必填、空数组 400**：显式优先；"什么都不采纳"不是采纳，是**拒绝**（有独立动作与必填原因）。
- **楼层联动必须提示**：`floor` 属档口，采纳会**连带改同档口所有菜品**；`differences[].affectsOthers` 标记该行，UI 高亮提示供二次确认（受影响菜品数由列表 `floorImpact` 给出）。
- **两段式档口确认不简化**：它是"错别字 → 重复档口"的唯一防线；宁可多一步确认。
- **不做批量采纳**（与 B2 / B3 同口径，一期不做）。
