# B3 · 举报管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**B UGC 治理**
> 状态：**已定稿** —— 2026-10-02 拍板：受理举报可**联动隐藏**被举报评价（一次调用）；列表/详情**内嵌被举报评价**；回执**按类型分流文案**并在受理时说明"对评价做了什么"。

## 介绍

处理学生提交的**评价举报**（`user_feedback` 中 `type='report'` 的行）—— **受理（并处置被举报评价）** 或 **不予处理**，并向举报人投递站内回执。

**职责边界**：只管**举报这条记录 + 对评价的处置联动**。

- **与 [B2 意见反馈管理](./B2-意见反馈管理.md) 同表同端点**（`user_feedback` 一表两用，见 [schema/user_feedback.md](../../../schema/user_feedback.md)），**按 `category` 分流列表**：B2 传 `feedback`、本页传 `report`；
- **评价本身的治理**（隐藏 / 恢复 / 删除）在 [B1 评价管理](./B1-评价管理.md) —— 本页只在**受理**时**联动隐藏**一次，不提供"恢复显示"（恢复走 B1）。

**举报数据形状**（写入侧已定，见 [api/reviews.md](../../../api/client/reviews.md)）：

举报落 `user_feedback`、以 `type='report'` 标别 —— **举报原因存字典原因 ID**（`sub_reason_id`，来自 [A7 举报原因管理](../A-主数据维护/A7-举报原因管理.md) 的字典，仅启用项可提交）、可带**可选补充说明**（结论以原因 ID 为准），关联目标固定为**被举报的评价**（`review` + 评价 ID）；列口径见 [schema/user_feedback.md](../../../schema/user_feedback.md)。

**前置规则（不变）**：

- **目标必须公开可见**：已隐藏 / 已删除的评价对外等价于不存在 ⇒ 提交举报返回 `4001`；
- **同一登录用户对同一评价不重复举报**（游客 `user_id = 0` 无身份标识，不去重）。

## 接口

**与 [B2](./B2-意见反馈管理.md) 完全同源**（同端点、同处理 DTO），差异只在"举报特有的字段与联动"。端点 / 入参 / 出参 / 错误码见 [**api/web/feedback.md**](../../../api/web/feedback.md)（本页**不新增端点** —— 菜单独立、端点复用）。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `user_feedback` | 读写（处置状态 / 回复 / 不采纳原因 / 处理时间） | 举报记录本体 |
| `review` | **写**（受理并联动隐藏时置为隐藏） | 联动隐藏被举报评价 |
| `dish` | 评分聚合经事件**重算** | 隐藏评价会影响菜品均分 |
| `notification` | **写**（处置回执） | 站内回执 |
| `user` | **只读**（举报人昵称 + 被举报评价作者昵称） | 双方展示 |

> 列口径见 [schema/user_feedback.md](../../../schema/user_feedback.md)。

> 隐藏评价**复用 B1 的同一套语义**（`is_hidden` 是唯一可见性判据、评分同步重算），不另立"举报隐藏"状态。

## 回执文案（**按类型分流**）

> 回执文案按 `type` 分流：举报人收到「举报已受理 / 举报未采纳」、反馈人收到「反馈已处理 / 反馈未采纳」，避免「反馈已处理」误用于举报人的语义错位。

| 结论 | 标题 | 正文 |
|---|---|---|
| `handled` + `hideReview=true` | **举报已受理** | `你举报的评价已被处理：已隐藏该评价` + （有 `reply` 时）`。处理说明：<reply>` |
| `handled` + `hideReview=false` | **举报已受理** | `你举报的评价已受理` + （有 `reply` 时）`：<reply>` |
| `rejected` | **举报不予处理** | `你举报的评价不予处理：<rejectReason>` + （有 `reply` 时）`。处理说明：<reply>` |

- **投递口径**：判据 `user_id > 0`（**静默登录的游客同样收到**；匿名提交 `user_id = 0` 不投递）；**失败不阻塞**处置；
- **为什么要说明"对评价做了什么"**：举报人拿到**闭环反馈**才有持续举报的动力 —— 这也是治理正循环的一环。

## 与当前代码的差异

> 本节集中登记与现有代码的差异；清零即写「无」。

- **`hideReview` 联动隐藏**：`FeedbackHandleReq.hideReview` 经幂等跨域契约 `ReviewService#hideIfVisible` 执行（评价不存在 / 已隐藏 → 返回 false，不重复投回执、不覆盖既有附注）。
- **举报行内嵌「被举报内容」摘要**：列表 VO 内嵌被举报评价摘要（举报原因经 [A7](../A-主数据维护/A7-举报原因管理.md) 字典翻译、端上零硬编码；含评价内容 / 菜名 / 是否已隐藏，据此在处置时把「同时隐藏」复选置灰）；批量补齐（只取所需列 + 菜名批量，一页 2 次查询，杜绝 N+1）；出参字段见 [api/web/feedback.md](../../../api/web/feedback.md)。
- **回执文案按 `type` 分流**：举报 →「举报已受理 / 举报未采纳」；反馈 →「反馈已处理 / 反馈未采纳」；受理且顺带隐藏了评价时正文写明「已隐藏该评价」。
- **列表走 `category=report`**（与 B2 共用的参数）。

## 备注（架构取舍）

- **三个菜单、一个端点**：举报与反馈**同表同流程**（提交 → 处理 → 回执），拆端点会把整套逻辑复制一份；**菜单独立**是因为列表字段与处置动作不同（举报要看被举报对象、要做联动）。
- **联动隐藏是"一次性动作"而非状态**：受理时隐藏；若要**恢复显示**（如误判），走 [B1 评价管理](./B1-评价管理.md) 的"恢复显示" —— 举报记录本身不持有"评价可见性"的状态。
- **`relatedReview.authorNickname` 对管理端开放**：与 `relatedDishName`（含已下架菜品名）同一取舍 —— 管理端处置需要定位责任人；**端上不得据此推断任何可见性**。
- **不做批量处置**（与 B2 同口径，一期不做）。
