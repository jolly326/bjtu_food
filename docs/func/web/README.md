## 项目约定与红线

> **效力**：任何新功能 / 改动若与本节冲突，**必须先修订本节（重新拍板）再动代码**。

### 定位

- **内部工具**：给校园运营（学生团队 / 后勤）录入与维护菜品数据、查看学生反馈。
- **不做**：用户管理（无封禁）、内容审核、数据导出、多角色权限。
- **单管理员**：无角色分级，不做按角色隐藏入口。

### 数据录入是唯一数据源

- 学生端**全部**菜品 / 档口 / 食堂数据**只能**由本站录入 —— 没有第二条写入途径。
- 因此 🔴 **录入质量 = 学生端数据质量**：名称、图片、位置必须准确。

### 唯一性（应用层保证）

| 范围 | 约束 |
|---|---|
| 食堂 | `name` **全局唯一** |
| 档口 | **同一食堂下** `name` 唯一 |
| 菜品 | **同一档口下** `name` 唯一 |

### 删除边界

| 对象 | 规则 |
|---|---|
| 食堂 | 🔴 **有下属档口时拒绝删除** |
| 档口 | 🔴 **有下属菜品时拒绝删除** |
| 菜品 | 可删；🔴 **连带清理**其点赞与纠错记录（外键 `ON DELETE CASCADE`）—— 删前须确认 |

### 反馈数据只读

- 点赞数据与纠错提交**运营端不修改、不删除**；点赞数在「菜品管理」列表内以只读派生列展示。
- 纠错的唯一动作是**标记已处理**（`handledAt`），且 🔴 **不给学生任何回执**。
- 菜品的 `likeCount` 是**派生缓存列**，运营端**不可直接修改**。

### 合规与不做的事

- 运营端**不展示任何用户标识**（学生全匿名）。
- **不做**操作日志 / 审计表（纠错处置只用一个 `handledAt` 时间戳留痕）。
- 图片（菜品图）**不送内容机审** —— 素材由运营自行上传。

### 明确**无入口**的表（防后人误加）

| 表 | 为何无入口 |
|---|---|
| `user` | 🔴 **全匿名设计的必然** —— 学生数据不在运营端展示（运营既不需要看，也不该看） |
| `admin` | 🔴 **单管理员** —— 账号行由**数据库直接维护**；**无注册、无自助改密**（见 [C1](./C-账号与访问/C1-管理员登录.md)） |

> 这两张表**刻意没有**查看或管理入口。若将来要加（如「用户数统计」「管理员改密」），**须先重新拍板**。
> 除这两张外，其余 **6 张表均有入口**：`canteen`→A1 · `stall`→A2 · `dish`→A3 · `dish_rating`→A3（只读，点赞数）· `dish_issue`→B1 · `dish_issue_option`→B1。
