# A7 · 举报原因管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**A 主数据维护**
> 状态：**已定稿** —— 2026-10-02 拍板：**数据锚在原因 ID**；**被举报记录引用过就禁止删除**（下线用停用）；**启用 ≤8 条**；**强制至少保留 1 条启用**。

## 介绍

维护 client **举报弹层的「原因」单选字典**（[`GET /report-reasons`](../../../api/client/reviews.md) 的数据源）—— `id`（原因 ID）+ `label`（中文）+ 顺序 + 启停。

**定位**：举报原因是**可维护字典**，新增原因**免发版、免客户端改动**（端上零硬编码，只消费 `id` / `label`）。

**职责边界**：只管举报原因字典。**举报记录的处置**在 B3（举报管理）；本页不碰举报记录本身。

**删除约束**：**被举报记录引用过就禁止删除**（`user_feedback.sub_reason_id` 存的就是原因 ID）—— 删掉会让**历史举报翻不出中文**。下线一律用**停用**。

**关键不变量**：**至少保留 1 条启用** —— 全部停用会让举报弹层变空、**举报入口瘫痪**（UGC 治理断链）。

**条数上限**：**启用 ≤8 条** —— 举报弹层是单选列表，太长不好选。

## 接口

端点 / 入参 / 出参 / 错误码见 [**api/web/report-reasons.md**](../../../api/web/report-reasons.md)（举报原因契约唯一真源）。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `report_reason` | 增删改查 | 举报原因字典本体 |
| `user_feedback` | **只读**：统计 `feedbackCount`（`type='report'` 且 `sub_reason_id = id`） | 引用计数（删除前判断） |

> 列口径见 [schema/report_reason.md](../../../schema/report_reason.md)。

## 客户端可见性

[`GET /report-reasons`](../../../api/client/reviews.md) 出参恰 `{ id, label }` 两项、无分页，内容由字典表驱动：

- 只下发 **`status='on'`** 的原因；
- 顺序 = `order` 升序（拖拽后的顺序）；
- **举报提交白名单查表**：提交时校验「该原因 ID 存在且**启用**」—— 停用的原因**不能再被提交**（但历史已提交的记录仍能翻译出中文）。

## 备注（架构取舍）

- **数据锚在原因 ID、管理员只填中文**：`label` 改名免费（历史举报的翻译随表实时生效）；与 [A4](./A4-菜品属性维度管理.md) 的维度 / 取值 ID、[A6](./A6-首页筛选视图管理.md) 的分类 ID 同源口径。
- **删除用"引用即禁删"而非级联**：与 A1 / A2 / A4 / A6 一致 —— 管理员必须显式把历史记录归到别的原因（或直接停用），不做静默改写历史。
- **强制至少 1 条启用**：举报是 UGC 治理的入口，不接受"把入口配空"这种状态。
- **排序一律「拖拽 + 批量端点」**：与 A4 / A5 / A6 同口径；新建项默认排最后。
- **上限 8 条**：单选弹层的可用性约束（不是技术约束）。
