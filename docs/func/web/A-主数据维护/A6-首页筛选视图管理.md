# A6 · 首页筛选视图管理

> 所属端：**管理后台（Web）** ｜ 鉴权：管理端 JWT 登录（见 [C1](../C-账号与访问/C1-管理员登录与访问控制.md)）
> 归属：**A 主数据维护**
> **口径要点**：后台维护首页筛选 tab 的**文案 / 显隐 / 归类**（**按菜品种类取数，免发版**），并维护**菜品种类字典**（独立字典表 [`dish_category`](../../../schema/dish_category.md)）。

## 介绍

维护 client **首页筛选栏** —— [`GET /dishes/views`](../../../api/client/dishes.md) 下发的那排 tab。

**定位**：首页筛选栏是**低频运营项**，但它是**纯数据**：一个 tab = 一行 [`dish_filter_view`](../../../schema/dish_filter_view.md)（文案 + 显隐 + 归类）。**种类维度的 tab 新增 / 编辑 / 删除都在后台完成，免发版、零代码**。

**两层模型**：

| 层 | 落点 | 职责 |
|---|---|---|
| **视图** | 表 [`dish_filter_view`](../../../schema/dish_filter_view.md) | 一个 tab 的全部口径（**文案 / 显隐 / 归类**）**全部落库** |
| **种类字典** | 表 [`dish_category`](../../../schema/dish_category.md) | 菜品「种类」字段（`dish.category_id`，存种类 ID）的**取值域**；视图通过 `category_id` **引用**它、**不派生**它 |

**职责边界**：只管首页筛选栏与种类字典；**不管**菜品本体（A3）、属性维度与取值（A4）、首页 Banner（A5）。

**明确不做（边界）**：

| 不做 | 原因 |
|---|---|
| **非种类维度的 tab**（折扣 / 上新 / 价格区间等） | tab 的取数口径 = **一个菜品种类**（[`dish_filter_view.category_id`](../../../schema/dish_filter_view.md)），**非种类维度没有落点** ⇒ 新增这类 tab **需要发版**（端上先支持该取数维度，再把口径落库） |
| **tab 排序口径可配** | 全部 tab **恒为随机排序**（会话种子伪随机序），不存在可配的排序口径 |

**约束**：**不允许停用 / 删除「最后一个启用的视图」**（否则端上筛选栏为空、无落地页）。

## tab 的取数口径

每个 tab 由**一个菜品种类**驱动（存 [`dish_filter_view.category_id`](../../../schema/dish_filter_view.md)）：

| tab | `category_id` | 取数 |
|---|---|---|
| **为你推荐** | `NULL` | 不按种类筛，取**全量在售菜品** |
| **种类 tab**（6 个） | 对应种类 ID | 该种类下的在售菜品（与种类字典的 6 条种子**一一对应**） |

> **种子初始 7 个 tab**（为你推荐 + 6 个种类 tab），后台可改文案 / 启停 / 改归类 / 删视图。
> **排序恒为随机**：全部 tab 均为**会话种子伪随机序**（端上传会话级 `seed`，端上不传排序参数、无排序入口）。
> 取值域由服务端校验（`category_id` 必须是已存在的种类 ID，**非外键**）；**tab 顺序一律按 `id` 升序**。

## 种类字典维护

菜品种类是**独立字典表** [`dish_category`](../../../schema/dish_category.md)：`dish.category_id` 存其 `id`（**单值、互斥、后台录入必填**），种类与菜品 **1:1**。维护入口在管理端 A3 菜品管理页头的「管理分类」抽屉（分类下拉旁）：

- **登记**：只填中文名（`name`），ID 由后端生成；
- **重命名**：改 `name` 全站生效（**数据锚在 `id`** —— `dish.category_id` 存的就是它，故改名免费）；
- **顺序**：按 `id` 升序（**无排序位、无排序入口**）；
- **引用计数**：= 引用该种类的菜品数（`dish.category_id = id`）；
- **无删除端点**：种类是 `dish.category_id` 的锚点，下线 = 改名 + 把菜品改到别的种类。

## 接口

端点 / 入参 / 出参 / 错误码见 [**api/web/views.md**](../../../api/web/views.md)（筛选视图契约）与 [**api/web/categories.md**](../../../api/web/categories.md)（种类字典契约）。

## 数据

| 表 | 读写什么 | 中文解释 |
|---|---|---|
| `dish_filter_view` | 增删改查 `name` / `category_id` / `enabled` | 视图本体（tab 的全部口径） |
| `dish_category` | 增删改查 `name`（登记 / 重命名；**无删除端点**） | 菜品种类字典 |
| `dish` | **只读**：统计 `matchedCount`（`status='on'` 口径）与种类引用计数 | 匹配数与引用计数 |

## 客户端可见性规则

[`GET /dishes/views`](../../../api/client/dishes.md) 下发 = **`enabled = 1`** 的视图，且：

- **匹配数为 0 的视图不下发**（避免用户点进空列表）；
- 顺序 = **`id` 升序**；
- [`GET /dishes?view=<id>`](../../../api/client/dishes.md)：**非法 ID → `400`**；**不传 `view`（如搜索页）→ 取首个启用视图（按 `id`）**。

> **端上首屏默认选中第一个 tab**；服务端**无"默认视图"概念**（无 `is_default` 标记）。
> **不允许停用 / 删除"最后一个启用的视图"**（避免下发规则自相矛盾）。
> **端上只认 `id` + 文案**：归类与排序全在服务端，端上零文案、零条件感知。

## 备注（架构取舍）

- **视图全在库、按种类取数**：tab 的文案 / 显隐 / 归类都是数据，种类维度的 tab 后台自助增删改 —— 运营不再需要发版；端上契约恒定。
- **非种类维度需要发版**（见「明确不做」）：把取数口径收敛成「一个种类」，换来的是**零代码管理**；代价是新的取数维度必须随端上发版一起上。
- **全部 tab 随机排序**：筛选栏是「换个视角看看」的入口，随机序让每次会话都有新鲜内容；端上不提供任何排序入口。
- **种类独立成表、数据锚在 ID**：`dish.category_id` 存种类 ID，改名免费；种类与描述属性是**两种不同关系、两个独立实体**（1:1 单值 vs m:n 多值），各有自己的表与端点，不共用 A4 的取值管理能力。
- **字典表一律不设排序位**：`dish_filter_view` / `dish_category` 与其他字典表一致，列表与端上下发一律按 `id` 升序（全站唯一保留排序位的是 `banner`）。
