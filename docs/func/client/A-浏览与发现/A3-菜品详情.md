> 归属：**A 浏览与发现**

## 介绍

看一道菜的**完整信息**（图、价、原价删除线、描述、荤素 / 主料 / 口味 / 冷热、食堂 · 楼层 · 档口名、**评分**）与**全部可见评价**。评价区**按时间倒序展示（新评价在前，唯一排序）**；写评价入口在**评价标题行右侧**，**重复提交即覆盖旧评价**（旧评价作废、留下最新，**`created_at` 保留原值、不因修改而置顶**）。评价分页加载的结束判据 = **本页返回条数 < `pageSize`**。

> 接口 / 字段见 [api/dishes.md](../../../api/client/dishes.md)。

**登录态与游客态返回结构完全一致**（无用户态分支）—— 详情与公开列表保持「纯公开」属性。
⚠️ **详情端点为「非幂等 GET」**（每次成功响应向 `dish_view_log` 写一条浏览明细）⇒ **详情不可缓存、不可 CDN 化**（缓存会让浏览量失真）；**公开评价列表**为纯读，可按需缓存。计数口径已登记进 [perf 基线](../../../perf/perf-00-度量口径与基线.md)。

## 展示口径

| 项 | 口径 |
|---|---|
| **评分展示** | 卡片与详情**只显示「⭐ 均分」**（`avgRating`）—— **保持简洁，不展示评价条数**；可信度交由「评价区按星级筛选」承载 |
| **零评价展示** | 出参 `avgRating` 兜底为 **`5.0`**、端上显示「⭐ 5.0」（冷启动期大量菜品零评价，评分位不得空缺）；🔴 兜底值**不落库、不参与排序**（评分无排序消费方，见 [schema/dish.md](../../../schema/dish.md)） |
| **评价排序** | **时间倒序（`created_at DESC`）唯一排序**，无切换入口；覆盖提交**不刷新 `created_at`** ⇒ 首次评价时间即固定位置，**反复修改无法刷到顶部** |
| **评价筛选** | 评价区提供 **1~5 星 + 全部** 筛选（类似美团），**服务端过滤**（`GET /dishes/{id}/reviews?rating=`）；切筛选**重置分页**；🔴 **零评价且未筛选时不渲染筛选条**（无可筛项）；🔴 **已选筛选但命中 0 条时筛选条仍保留**（否则「全部」入口消失、用户无法回退 ⇒ 死路） |
| **零评价号召** | 评分位恒显「⭐ 5.0」而评价区此时为空 ⇒ 两者并置会显得矛盾（卡片说 5 分、详情说没人评）⇒ 零评价时评价区显示 **「快来抢首评 ⭐ 5.0」**（**不显示**「暂无评价」），把「矛盾」转为**冷启动号召** |
| **折扣判定** | `originalPrice > price` 即有折扣 —— 两态表达，**无独立「折扣价」字段**；端上算的业务判定 |
| **属性渲染** | 逐维渲染、**缺项不占位**（不得出现 `-` 空列凑满）；值为中文（服务端由取值 ID 翻译下发），端上零翻译 |
| **位置表达** | 仅用 **食堂名 · 楼层 · 档口名**；不出参坐标、不算距离、不申请定位权限 |
| **空值兜底** | 字符串字段恒非空（服务端空串兜底）、`images` 恒为数组；**仅** `originalPrice` 有意可空（`avgRating` 恒非空） |
| **不展示** | 评分进度条 / 分布条、评价条数、距离、窗口号、「信息更新于 X」 |

## 异常处置

| 场景 | code | 端上处置 |
|---|---|---|
| 菜品不存在 / 已下架 | `4001` | 展示「菜品不存在」+ **返回首页** |
| `id` 非数字 | `400` | 按「不存在」处理 |
| 提交校验失败（内容安检等） | `400` | **Toast 透出服务端 `message`**；表单保留、不清空 |
| 网络 / 服务端故障 | `5xx` | 展示**可重试**失败态（与「不存在」**区别对待**） |

## 设计决议

**写评价：无「写前判定」，无「重新评价」双态。**

- **详情页零用户态请求**：仅「详情 + 公开评价」并行，游客与登录行为完全一致；详情页**不调** `GET /my/reviews?dishId=`（该端点服务于「我的评价」页）；
- **提交动作**：点「写评价」→ **直接打开空表单**（不预填旧值、不显示覆盖提示）→ 提交恒 `POST /dishes/{id}/reviews`；**同一用户对同一菜品的重复提交由服务端覆盖旧评价**（端上不感知首评 / 重评），且**覆盖不刷新 `created_at`** —— 改评价不会把自己顶到列表首位，因此**不设提交限频**（见 [api/dishes.md](../../../api/client/dishes.md)）；
- **提交失败处理**：`400`（参数 / 安检等校验失败）⇒ **Toast 透出 `message`、弹层不关闭**（保留已填内容）；`4031` ⇒ 跳身份认证页；**`4001`（菜品不存在 / 已下架）⇒ 关闭弹层 + 返回首页**（不可重试）；
- **按钮文案恒定**：评价标题行右侧按钮**恒为「写评价」**（无「重新评价」态）；
- **评价作者标识 `userId`**：公开评价出参携带，端上据此决定评价卡「删除 / 举报」入口显隐（服务端另有「非本人 → 403」鉴权）——**保留 `userId`，不引入 `isMine`**：`isMine` 须由服务端按请求者计算，会让公开评价列表变为「半用户态」；本人视角下恒真属零信息冗余。**有意的双重判定权衡。**

**R14（`userId` vs `isMine`）：采用 `userId`，不设 `isMine`。**

端上持有「当前用户 id」并与 `userId` 比对，决定「删除 / 举报」入口显隐（服务端另有「非本人 → 403」鉴权）：

1. `isMine` 须由服务端**按请求者**计算 → 会让**公开评价列表变为「半用户态」**（需解析可选 token），与 **R3**（保持详情与公开列表的「纯公开」属性）**直接矛盾**；
2. 在本人视角（`GET /my/reviews`）中 `isMine` **恒为 `true`** —— 恒真字段，属零信息冗余；
3. `userId` 是公开列表**本就该下发**的作者标识（头像 / 昵称归属所需），端上做一次比对不引入新真源。
