# D1 · 系统通知（处理回执）

> 所属端：**学生端（微信小程序）** ｜ 鉴权：**🔑 需登录**（游客态亦可，不要求邮箱认证）
> 归属：**D 系统与合规**
> 返回：[功能总览](../README.md)

## 介绍

接收**管理员处理反馈/举报、菜品问题反馈处置、评价隐藏/删除后的回执**（**有 `userId` 即投递**：静默登录的游客与已认证用户同权；**匿名提交（`user_id = 0`）不投递**）。服务端按业务源（反馈处理与举报处置 / 菜品问题反馈处置 / 评价隐藏 / 评价删除）构造回执正文，**不存储类型键**——通知卡只渲染「标题 + 正文 + 时间 + 未读态」，**不按类型分支、不做类型相关跳转**（将来要做「按类型跳转」须先由 UI 文档定义交互，再新增 `type` + `related_id` 列，命名以 [schema/notification.md](../../../schema/notification.md) 为准）。管理员处理反馈或菜品问题反馈时投递，正文含回复内容（不采纳时含不采纳原因）；**游客提交的反馈 / 举报 / 菜品问题反馈同样投递回执**（不阻塞处理）。进页拉取通知列表（默认全部，可筛未读），点开单条即标记已读，支持一键「全部已读」（幂等，无载荷）；无通知时展示空态。

> 接口 / 字段见 [api/my.md](../../../api/client/my.md)。

> **路径风格登记**：`read-all` 为**动作式路径**（非资源化的 `read-status`）—— 与同族的 `/{id}/read` 同构，该端点为幂等批量动作、无请求体，动作式命名歧义更小。**保持现状**。

## 业务口径

| 项 | 口径 |
|---|---|
| **内容来源** | 管理员处理反馈 / 举报 / 菜品问题反馈后的**回执**；正文含回复内容（不采纳时含不采纳原因） |
| **鉴权级别** | **有 `userId` 即投递**（静默登录的游客与已认证用户同权）；**匿名提交（无 token，`user_id = 0`）不投递** |
| **不按类型分支** | 通知卡只渲染「标题 + 正文 + 时间 + 未读态」，**不按类型分支、不做类型相关跳转**。将来要做跳转须先由 UI 文档定义交互，再新增 `type` / `related_id` 列（与 [schema/notification.md](../../../schema/notification.md) 一致） |
| **已读口径** | 点开单条即标记已读；「全部已读」幂等，无载荷 |

## 端上取数口径

未读数由端上统一状态持有并驱动红点：

| 项 | 规则 |
|---|---|
| 请求合并 | **in-flight 合并 + 10s TTL 去重** —— 页面来回切不重复请求同一数据 |
| 读后刷新 | 本地读操作（单条已读 / 全部已读）后**强制刷新**，保证红点即时准确 |

## 数据（读写）

| 表 | 变化 | 中文解释 |
|---|---|---|
| `notification` | SELECT / UPDATE `is_read` | 通知列表、红点计数、单条与全部已读 |
| `notification` | INSERT（由反馈处理 / 举报处置 / 菜品问题反馈处置 / 评价隐藏删除触发） | 处理反馈或处置举报写 `feedback_handle`、处置菜品问题反馈写 `correction_handle`（**标题按 `type` + 结论四档**：`field` 采纳「菜品信息已更新」／`field` 驳回「菜品信息未采纳」／`gone` 下架「菜品已下架」／`gone` 驳回「菜品仍在售」）、隐藏评价写 `review_hidden`、删除评价写 `review_deleted`；**游客提交同样投递**；⚠️ **账号被禁用时不投递任何回执**（禁用后无法登录、看不到通知） |
